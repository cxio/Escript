# 栈脚本设计

从更宽泛的意义上看，脚本就是合约，而合约是自由的。

本设计包含了完整的流程控制语法，如：`IF`、`ELSE`、`SWITCH`、`CASE`、`EACH`（有限循环），运算操作符如：`+`、`-`、`*`、`/`，数据类型如：`Bool`、`Int`、`Bytes`、`String`、`Float` 等。总体上，这是一个准图灵完备的**栈脚本**语言。

在栈脚本中，所有的操作都基于已明确定义指令，没有自定义函数。所以相比于其它语言，栈脚本风险更小，且结构简单，便于审计。


## 基本概念

### 数据栈

存放脚本指令入栈数据和*返回值*的一个栈式空间，遵循后进先出（LIFO）的逻辑。脚本指令从数据栈获取*实参*，返回值则可能入栈。

这是常规的栈语言逻辑，实际上存在一个问题：*指令的实参取值严格受到前一指令返回值的约束！*

这让指令的实参安排十分窘迫，严格的顺序导致指令排挤，要求较高的耦合性，让栈脚本的灵活性很差。所以有了**实参空间**的设计。

> **实现：**
> 数据栈是一个简单 `[]any` 结构，进入数据栈的具体类型都会自动转为 `any`。


### 实参空间

实参空间也叫**实参区**，是临时存放指令实参的一个腾挪区域，规则是这样：

*如果指令需要实参，系统会先从该实参区取值，如果无值，再从数据栈取值。*

这样，指令的实参就可以提前取出，让出栈条目位置，避免栈顺序对后续指令的排挤。并且由于实参可以从栈的任意位置获取，指令的安排就可以很灵活了。它解耦了指令的顺序关系。

实参区是一个队列，可以持续地向里面添加条目，但取出则是*一次性*的（简单性考虑）。


#### 指令的参数配置

每个指令需要配置其实参的取值数量：

- **`0`**： 无需实参。系统不会读取实参区。
- **`n`**： 固定数量。从实参区取值，如果无值则从数据栈获取。实参区里的条目数必须匹配（一次性取出）。
- **`-1`**：不定数量。如果实参区有值，则取出，否则取空值。因此不会访问数据栈。
- **`-2`**：半确定性。特用于 CALL 指令。实参数量由其附参设置，非系统级静态配置。


### 附属参数

简称**附参**，主要是对指令本身的描述（静态，类似于属性），紧跟在指令之后。比如 `IF` 指令，附参定义了其代码块的长度。

附参是一种基础设计，它能更完整地表达指令（也可提升效率）。


#### 附参vs实参

对于部分指令，其需要的参数可能并不那么像*属性*而更像*实参*，但最终它被设计成了附参。

这是源于附参静态特性的优势，如果这个参数静态化更好，比如 `GOTO` 指令的跳转目标不应当动态化（安全风险），就需要把它设计为附参。


### 关联数据

指令关联的内容，比如 `IF{}` 指令的子语句块，值指令 `DATA{}` 所携带的字节序列等。

关联数据是指令除了附参和实参之外，直接拥有或控制的数据。


### 局部域

一个有限的储值空间。存在于每一个语法块内，与普通的编程语言不同，它只能在当前域访问（块级私有）。

> **附：**
> 另外也有一个全局域的储值空间，可以从任何位置访问。


### 自动展开

部分指令会有多个返回值，系统会将它们自动展开到目标位置（数据栈、实参区或局部域等）。

> **注：**
> 这样的指令并不多，主要是完成一些特殊操作（如栈操作）。


### 缓存区和外部监听

脚本支持与外部的交互（`INPUT`、`OUTPUT`），导出和导入通过两个完全独立的缓存区完成。

- **INPUT**:  公共验证域即时中断（同 END），不影响 PASS 状态。私有域下，数据由外部环境注入，无数据即时中断。
- **OUTPUT**: 非阻塞导出。有一个临时缓存区，可以接受多次 OUTPUT 积累数据，直到遇到 BUFDUMP 指令转出/清空其数据。
- **BUFDUMP**: 转出**导出缓存区**数据到外部环境。通常外部应当注册监听，转出触发驱动，然后中间件接手处理外部业务。

> **注意：**
> INPUT/OUTPUT 连接的是两个各自独立的通道，两个缓存区并不互通。它们主要服务于链外事务。
> BUFDUMP 监听是私有的，只有需要的节点才会去部署。

导入指令稍有特别，对于公共验证节点实际上是一个隐式的 `END`，因为这些节点不会 INPUT 任何外部数据。



## 脚本指令集

### 指令码

每个指令都有一个值对应（指令码），脚本就是指令及其数据的**值序列**。

指令码用**1**个字节来表达，因此基础指令集最多不超过**256**个指令。但指令集里包含了扩展指令本身，因此逻辑上可以无限扩展。

指令集分为如下四个块段：

1. **基础指令段**：包含如流程控制、数学运算、栈操作、模式匹配等功能指令集。码位 `[0-169]`，共 **170** 个。
2. **函数指令段**：包含高频和常用的基础功能函数，以及1个自扩展指令。码位 `[170-220]`，共 **51** 个。
3. **模块指令段**：定义一些基本和标准的模块，以及1个自扩展指令。码位 `[221-250]`，共 **30** 个。
4. **扩展指令段**：专用于指令的扩展引用，包括1个模块扩展和1个私有扩展。码位：`[251-253]`，共 **3** 个。


### 指令命名

根据指令的特性，划分出了如下5个大类别：

1. 基础功能。指令名无前缀，视觉简洁。如：`PASS`、`IF`、`TRUE` 等。
2. 系统调用。指令名有前缀 `SYS_`，如：`SYS_TIME{}`、`SYS_AWARD` 等。
3. 功能函数。指令名有前缀 `FN_`，如：`FN_CHECKSIG`、`FN_PUBHASH` 等。
4. 模块引用。指令名有前缀 `MO_`，如：`MO_MATH`、`MO_FMT`。
5. 扩展定制。指令名有前缀 `EXT_`，如：`EXT_MO`、`EXT_PRIV` 等。


### 书写约定

脚本在人工编码或阅读时，需要遵循友好的格式。以下是一些约定：

- `{}` 包围指令的关联数据，比如IF语句的子语句块。
- `[]` 包含指令附参的值，非必要时可省略。如：`DATA[20]{...}` 可简写为 `DATA{...}`。
- `()` 文档说明中表达指令附参的长度。如 `DATA{}(1)` 表示指令的附参为1字节。**注**：花括号表示指令有关联数据。
- `<>` 表示命名数据，如：`<pubKey>` 指一个公钥，`<sig>` 表示签名数据。

> **注：**
> 链上的脚本已经被编译为指令值序列，文本是解译后的显示。


### 指令类别

从指令的属性（干什么）上看，有如下的类别区分：

1. **值指令**。脚本中的一个实际的值，会自动入栈。如：`TRUE`、`DATA{...}`。
2. **截取指令**。拦截跟随指令的返回值，将它们放到目标位置。如：`@`、`&`、`~`、`_`。
3. **栈操作指令**。直接操作数据栈中的条目，如：`PUSH`、`POP`。
4. **集合指令**。对值集合的简单操作，如：`SLICE`、`MERGE`、`SPREAD`、`INDEX`。
5. **交互指令**。与外部的交互，通过两个独立的缓存区完成。指令如：`OUTPUT`、`INPUT`。
6. **结果指令**。表达确定的结果，如通关指令 `PASS`，或跳转指令 `GOTO`，以及 `RETURN` 等。
7. **流程控制**。控制执行流，包含：`IF{}`、`ELSE{}`、`EACH{}`、`BREAK` 等。
8. **转换指令**。值类型转换，包含：`BOOL`、`FLOAT`、`STRING` 等。
9. **运算指令**。简单的数学运算（`+-*/%`），以及其它计算，如：`REP`、`DEL` 等。
10. **比较指令**。比较操作支持，如：`EQUAL`、`GT`、`WITHIN` 等。
11. **逻辑指令**。逻辑操作支持，如：`BOTH`、`EITHER`、`SOME` 等。
12. **模式指令**。检查脚本自身的能力，主要是一些模式匹配测试：`MODEL{...}`、`#`、`_`、`?`、`...` 等。
13. **环境指令**。从环境中获取信息的支持，如：`IN{}`、`OUT{}`、`VAR`。
14. **工具指令**。实用功能的简单支持，如：`EVAL`、`COPY`、`MATCH`、`RANGE`、`FILTER`。
15. **系统指令**。系统级的功能支持，如：`SYS_TIME`、`SYS_CHKPASS`。
16. **函数指令**。常用的基础功能函数,如：`FN_PUBHASH`、`FN_CHECKSIG`、`FN_BASE32`。
17. **模块指令**。常用的基础模块，如：`MO_MATH`、`MO_FMT`。
18. **扩展指令**。宽泛的通用扩展机制，如：`EXT_MO`、`EXT_PRIV`。


### 特性指令

下面这些指令相对于常规的逻辑，有一些本脚本系统特有的特性，此专项罗列。


#### 系统域

- `SYS_NULL`: *跨域使用*。可在解锁脚本中使用，突破解锁段可用指令（opcode: `0-45`）限制规则。
- `SYS_CHKPASS`: *环境取参*。从系统环境读取实参。交易的解锁见证信息会被导入环境（而非进入脚本栈）。
- `DICT`: 唯一需要实参的「值指令」，动态构造。且允许运行时可变（`SET`|`DEL`|`CLEAR`）。
- `INPUT`: 公共验证域隐式 END。之后即为私有应用逻辑。
- `MODEL`: 指令码模式匹配，内部的普通指令语义为「匹配」而非执行。且返回值有两种状态。


#### 私有专属

少量具有不确定性的原生基础指令，不能用于公共验证（共识）域。因为其基础性，由系统级支持，为第三方私有应用提供便利。

- `{}(1)` 浮点数值指令（`opcode:7`）。
- `SYS_TIME` 获取本地当前系统时间。
- `SHELL` 本地脚本嵌入。支持第三方灵活的私有逻辑。
- `FN_PRIV`, `MO_PRIV`, `EXT_PRIV` 私有函数、模块、扩展专用预留空间。

这些指令如果在执行公共验证时遇到，即立即失败。验证不通过。用户构建脚本时需留意并自行负责。


#### 用户级实参配置

`CALL` 指令的实参数量由*附参*指定，在用户编写脚本时确定，而不是在系统级硬编码配置。


#### 自动展开

该部分的指令会返回多个值，会自动展开到目标空间（数据栈|实参区|局域）。

- `POPS`: 作为栈操作指令，自动展开取出的多个条目。
- `TOPS`: 作为栈操作指令，展开引用的多个条目。
- `PEEKS`: 作为栈操作指令，展开栈任意段的连续多个条目（引用）。
- `PUSH`: 作为主动入栈指令，实参区条目按顺序各自入栈。
- `SPREAD`: 手动展开作为实参的一个切片。
- `INPUT`: 导入外部数据，多个条目时自动展开。
- `DIVMOD`: 作为运算指令，返回两个值（商和余数），展开为两个值。
- `REP`: 作为运算指令，返回重复的值，展开到目标区。
- `MODEL`: 返回两个值时，自动展开。
- `MODEL/#,$`: 匹配&取值。有匹配取值时返回两个值，自动展开。
- `COPY`: 作为工具指令，返回浅复制的两个字典。自动展开。
- `KEYVAL`: 根据附参有多种返回值形式，两个返回值时会自动展开。


#### 空操作（公共域）

`PRINT`、`FN_PRINTF`、`OUTPUT`、`BUFDUMP` 几个指令会向节点的本地系统输出内容。对于公共验证节点来说，它们默认都是空操作。

如果有公共节点愿意接受输出，或者监听 `BUFDUMP` 的内容（公私用途兼具），它们可以自己配置开启。


### 附：系统占位符

码值 `254/255` 不用于上面的指令码规划，它们备用于可能需要的系统级功能。

系统占位符使用码值 `254`，用于指代脚本中定制验证需要的见证信息。

- 该指令只能存在于解锁脚本中，出现在其它位置（锁定脚本、外部引入的脚本、`EVAL` 执行的代码）即失败。
- 用户编写解锁脚本时，用系统占位指令指代相应的数据条目，如签名 `<Sig>`。
- 执行到占位指令时，系统从环境中取出对应的见证条目压入数据栈，效果与一条值指令相同。
- 脚本的字节码本身不改写：`SOURCE`、`IN{Unlock}`、`IN{Source}`、NULL 点、`MODEL` 和解锁脚本长度，都按含占位指令的原始字节计算。
- 用户提供的原始解锁脚本（含占位指令）用于签名消息的实际内容。

这样，就可以解耦签名消息和签名本身的自我依赖问题（签名结果需要成为签名目标消息的矛盾）。

```go
码值    标识符          说明
-----------------------------------------------------------
254     <...>(1)        签名相关实参占位
        // 附参：标识索引值
        // 名称首字母大写，与普通的驼峰名称（示意）相区别。
        // 标识名：
        // <Sig>        单签名数据
        // <PubKey>     单公钥
        // <Sigs>       多签名数据集
        // <PubKeys>    多签名公钥集
        // <Rests>      剩余公钥集（初级哈希）
        //
        // 说明：
        // 以上名称用于标准化表达（书写&反编译显示）。
        // 实际的指令码和附参存在于解锁脚本中。
        // 执行时，系统按附参从环境中提取相应数据项入栈（字节码不改写）。
        //
        // 设计：
        // <Sig>/<PubKey> 对应 FN_CHECKSIG；
        // <Sigs>/<PubKeys>/<Rests> 对应 FN_MCHECKSIG。
        // 没有签名参数中“授权标识”的占位符，它实际存在于解锁脚本里。
```



## 脚本的执行

脚本的执行是一个线性的过程，从脚本的起始位置开始，逐条解释指令并执行，直到脚本结束或遇到终止指令（如 `EXIT`），或出错退出。

总的原则：在执行的过程中，脚本本身是只读的，不能被修改。出错后验证为失败（不通过）。


### 解析规则

「解锁段」与「锁定段」之间只共享数据栈：

- 解锁段结束时，实参区必须为空，否则验证失败。
- 锁定脚本从一个新的顶层局部域开始，解锁段的局部域丢弃。
- `SOURCE` 的取码视图不受影响，仍可以把「解锁 + 锁定」当作一段源码提取。

解锁段与锁定段不共享实参区和局部域，原因如下：

- 实参区条目提取会跳过锁定段无实参取值的指令，而这些指令的返回值自动入栈。脚本编写者可能只关注了数据栈取值的逻辑，而忽略了解锁段可通过实参区向后传值（如果共享）。这容易导致脚本的编写出现漏洞。
- 局部域共享也有类似的问题：解锁段设置局部变量即可扰乱局部域存值的堆叠顺序。虽然局部域共享可以带来灵活性，但数据栈本身的取值已经十分灵活，因此局部域共享的灵活性价值不高，反而容易导致问题。


### 未知码位处理

如果系统升级，当前未用的码位可能有了功能定义，这会带来分叉的问题。

为了避免共识割裂的「硬分叉」，尽可能让分叉柔性（软分叉），让暂未升级的旧节点升级之后即可追随主链。对未知码位实行「宽松通过」的规则：*当解析器在锁定方的脚本中遇到当前版本未分配的指令码或附参索引时，整个验证即为通过，不再执行*。

这可以带来「**新严旧宽**」的效果：旧节点宽松通过，当更新后，不合法的交易/区块不再有效，从而必须同步为新版本的区块和交易。

宽松通过只适用于锁定方的脚本，即锁定脚本，以及 `GOTO`、`EMBED` 引入的脚本：

- 解锁脚本和 `EVAL` 执行的代码中遇到未分配的码位，一律失败。否则花费者只需在解锁脚本里，或交给 `EVAL` 的代码里放一个未分配码位，就能直接通过。
- `CALL` 的方法名是运行时的字符串，不适用此规则：调用当前版本中不存在的方法即失败。
- 码值 `255` 永久保留，遇到即失败。

> **注：**对未知版本的处理也与此相同。


### 例：币金支付验证

这是一笔标准的单签名币金支付（使用内置验证）。

输入引用资金来源的锁定脚本，花费者需要提供解锁数据（此仅需「见证信息」）。

```go
// 见证信息：
// 会导入系统环境，而非走数据栈通道。
{1}             // 签名类型（1|2），此为单签
<flag>          // 授权标记
<sig>           // 签名数据
<pubKey>        // 公钥

// 锁定脚本：
// 会从输入源读取花费者（来源输出的接收者/公钥哈希）
// 会从系统环境中读取见证信息。
// 验证：SYS_CHKPASS(<pubHash>, 1, <flag>, <sig>, <pubKey>, nil)
SYS_CHKPASS
```

> **注：**
> 与 Bitcoin 不同，本设计支持内置验证（而非纯脚本验证）。


### 例：定制验证

如果用户想要将验证逻辑书写在脚本里，也可以像下面这样：

> **概念：**
> 在逻辑上，解锁数据包含「见证信息」和「解锁脚本」两个部分。
> 如果用户将见证信息嵌入解锁脚本（而非导入环境），则视为解锁脚本内容。

```go
// 解锁脚本：
<flag>              // 授权标识
<Sig>               // 签名（占位符，执行时入栈签名）
<PubKey>            // 公钥（占位符，执行时入栈公钥）

// 锁定脚本：
TOP                 // 引用栈顶项（不弹出）返回入栈
FN_PUBHASH          // 取栈顶项计算公钥哈希后入栈
DATA{46af3fb4...}   // 预置的公钥哈希序列入栈
EQUAL               // 取栈顶2项相等比较，结果（true|false）入栈
PASS                // 取栈顶项检查，true 时通过，否则失败
@POPS[3]            // 取栈内3项：<flag>, <sig>, <pubKey>（签名/公钥已入栈）
FN_CHECKSIG         // 用实参区3项验证签名。结果（true|false）入栈
PASS                // 取栈顶项检查，true 时通过，否则失败
```

> **注：**
> 此时来源输出中的的接收者被忽略，但可用于友好展示。
> 解锁脚本中的 `<Sig>`、`<PubKey>` 是系统占位符（码值 `254`），执行时从见证信息取值入栈，见「附：系统占位符」。



## 安全性

脚本系统通过硬资源上限（参数限定）、执行成本预算、区块总成本限制和一些其它措施（与脚本逻辑无关）共同控制负载。


### 参数限定

区块链是一个开放的系统，恶意的攻击者可能构建十分消耗资源的交易，因此这里需要设置一些限制：

- 数据栈高度：`< 256`。脚本在运行过程中，数据栈内的数据大多会被即时使用，所以容量不需太大。
- 栈数据项大小：`< 8KB`。包容抗量子算法签名数据量，Script 类型数据（源码类）特别允许最高 `16KB`。
- 锁定/识别脚本长度：`< 8KB`。
- 解锁脚本长度：`< 8KB`。**注**：不含标准内置验证（`SYS_CHKPASS`）所需的见证信息；定制验证的签名/公钥只是占位符（几字节）。
- 描述/内容：`< 2KB`。凭信的描述和存证的内容，限制长度避免恶意填充数据。
- EMBED嵌入次数：`<= 4次`。运行时计数。
- EMBED嵌入深度：`== 0`。即嵌入的脚本不可再有嵌入（`EMBED`）和跳转（`GOTO`）。
- GOTO跳转次数：`<= 2次`。每个脚本各自计数，运行时信息。
- GOTO跳转深度：`<= 3次`。从主脚本到子孙脚本，运行时计数。**参考**：管理者+审计者+第三方。

脚本的指令序列是顺序执行的，不可回退（没有返回到前端位置的指令），因此一个固定长度的脚本必然终止，开销由成本预算约束。

> **注意：**
> 对于锁定脚本的长度限制检查包含两项：
> 1. 作为输入项的引用源输出的锁定脚本，脚本长度已成事实。不限制。
> 2. 当前交易中每个输出项的锁定脚本。如果超过限制，交易将被拒绝。用户有机会调整脚本以满足要求。


### 执行成本

脚本的执行还应受到成本预算约束（协议层）。

每条指令将根据：数据长度、签名验证、哈希计算等因素折合计算量（内存占用单列），消耗一定成本。脚本执行过程中累计成本超过限制时，视为失败（交易被拒）。

成本核算分三层：

1. 单个输入的最大成本（MaxInputScriptCost）。
2. 单笔交易的最大总成本（MaxTxScriptCost）。
3. 单个区块的最大总成本（MaxBlockScriptCost）。

这会增加脚本系统的复杂性，但为防止恶意攻击，不得不有的一种妥协。通常，成本上升交易费应当更高，但这只是一种理性，如何取舍由铸造者决定。

> **注记：**
> 暂不设计交易费随成本上升而增加的协议级机制（初期简化）。


#### 实现参考

指令成本可能实现为函数，根据实际参数动态计算，以真实反映资源消耗。但注意：

**成本函数返回的是确定性的值，它只与指令的性质有关，而与硬件环境无关。**

这应该是一种综合性的评估，确定了成本计算因子和算法之后，便固定下来，不再调整（逻辑上）。

> **注：**
> 可能实现为每个指令都有一个成本函数，相似成本的指令可以共享同一个函数。


### 锁定&解锁

#### 解锁数据

解锁数据包含用于标准验证所需的*见证信息*和通用的*解锁脚本*两部分，后者主要用于合约需求（或定制验证）。

解锁脚本中可以使用的指令是有限制的，它被严格限制在指令码值 `[0-45]` 的区段，即：值指令、截取指令、栈操作指令和集合指令。这是为了保证解锁脚本的安全性，但同时也提供必要的操作灵活性。

> **注：**
> 如果没有限制，一个 `TRUE PASS EXIT` 序列即可无条件通关。

> **特例：**
> 系统级指令 `SYS_NULL`（opcode 169）和系统占位符（码值 254）作为例外可以在解锁脚本中使用。


#### 边界处理

解锁段与锁定段之间只共享数据栈，局部域与实参区不可跨越：

- 解锁段结束时，实参区必须为空，否则验证失败。
- 锁定脚本从一个新的顶层局部域开始，解锁段的局部域丢弃。
- `SOURCE` 的取码视图不受影响，仍可以把「解锁 + 锁定」当作一段源码提取。

解锁脚本和锁定脚本需要分别解析，任何指令（包括 DATA 的长度、块长度）都不能跨越两段的边界。



## 附：源码的格式

源码应当有良好的格式，以便于阅读和书写。

像大部分程序语言一样，换行和缩进是自由的，但指令之间仅以空白（空格/制表符/换行等）分隔。


### 指令码的解译显示

脚本指令序列解译为文本展示时，遵循如下换行和缩进规则。

- **子块缩进**：包含子语句块的结构指令会将内容换行并缩进显示。
- **行长限制**：连续的指令显示不宜太长，必要时换行。
- **独行指令**：包含较长值的指令通常显示在单独一行，比如：`DATA{}`、大整数或正则表达式等。
- **行尾指令**：显示在行尾时含义更清晰，比如：`PASS`、`RETURN`、`EXIT` 等。
- **跟随指令**：与前阶指令紧密相关，应当显示在同一行。如模式指令中的取值 `#(1)`、带实参的 `@POP RETURN` 等。
- **前缀指令**：是后阶指令的前置指令，应当与后阶指令紧邻。如截取指令：`@`、`~` 等。

如果行长限制与其它规则冲突，视情况灵活处理，如折行或提前换行。



## 附：SYS_CHKPASS 超级赎回

`SYS_CHKPASS` 是一个内置的系统验证指令，用于验证交易输入的见证信息（签名），从系统环境取实参（见证信息会在执行解锁脚本之前导入环境）。

因为是系统级指令，所以实际上可以提供某些特定功能。

在区块链长期运行之后，其 `UTXO/UTCO` 集可能十分庞大，其中绝大部分应该是正常的未花费输出，但也可能积累实际上已经无法花费的「死钱」，比如解锁脚本中包含了过期的时间条件，无论如何执行，都不会通过验证（过期锁死）。

这些脚本通常都是无心之过，极少数也可能因为某种网络大面积割裂导致分叉，从而引发的连带后果。这些 `UTXO/UTCO` 无法再花费，既会成为数据集的负担，对用户来说也是一种损失。

因此这里提出一种补救措施：*在 `SYS_CHKPASS` 里植入一种赎回机制*，详细规则如下：

- 帮助取回无法花费的 `UTXO`，或者清理无法消费的 `UTCO`。
- 有一个开关，如果打开，`SYS_CHKPASS` 系统级验证通过后，即结束脚本。因此后续原锁定脚本不再运行，解耦锁死。

超级赎回主要针对 `UTXO`（未花费币金输出），因为 `UTCO`（未消费凭信输出）实际上有一个系统级的超时过期机制（百万区块高度，约 11.4 年），并非真的永久。但清理 `UTCO` 也是有价值的。

> **局限：**
> 仅适用于使用 `SYS_CHKPASS` 标准验证模式的锁定脚本，且 `SYS_CHKPASS` 置于锁死逻辑之前。


### 触发条件

- 如果 `SYS_CHKPASS` 接收到一个**特权签名**，开关即打开。
- 特权签名由特权私钥执行，特权私钥的公钥由社区发布，并且需要通过核心 App 全网升级更新完成。
- 特权私钥最多只有**1**年有效期，之后如果需要更新，需重复升级流程。这由社区人类共识决定。


### 结构约束

- `SYS_CHKPASS` 的输入参数里，依然需要原始输出项的普通签名。两个签名同时提供，也即：超级赎回需要双方合作才能完成。
- 新交易的输出项只有单一目标：原输出项的接收者，或者一个新的地址。但只有单一输出。这可以简化交易、审计，以及可能有的博弈。
- 回收的 `UTXO/UTCO` 项必须在 **100_000**（10万）个区块之前，即仅适用约一年零两个月之前历史交易。
- 必须是 `UTXO/UTCO` 中已经确认无法回收的条目。这些条目会作为白名单硬编码进升级后的 App 里（采用省空间的索引）。

这属于由社区（人类）主动参与的异常情况处理，但它可以很干净地解决 `UTXO/UTCO` 条目锁死的问题。

> 这是一个可选的想法。供后期视现实情况参考。
