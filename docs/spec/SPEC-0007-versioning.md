# SPEC-0007 版本与升级

## 概述

每个锁定脚本有一个版本号，由创建输出的人决定。一个版本冻结一组表；表中未分配的码位和索引，在锁定方的段中宽松通过，在解锁段和 EVAL 代码中失败。这使新功能可以在原版本内以软分叉加入锁定方的段，而凡是需要放宽规则的变化都必须发布新版本。

本篇规定版本号的来源与比较、每段的版本、版本冻结的内容、宽松通过的范围、未知版本的处理，以及规格维护者在升级时必须遵守的规则。


## 规格正文

### 1. 版本号

- 版本号由锁定方决定，花费者不能选择（DEC-0004 第 1 条）。
- 版本号放在宿主的输出结构中，不放进字节码。宿主规格规定从输出结构中的哪个字段取得版本，以及该字段的取值与核心版本号的对应（Evidcoin：输出项的版本字节〔P-09〕）。
- 核心版本号是从 1 开始递增分配的正整数〔R-14〕。宿主字段的取值映射不到任何核心版本号，或映射到本节点不认识的核心版本号，都是**未知版本**。未知版本大于本节点认识的任何版本。

### 2. 每段的版本

| 段 | 版本 |
| --- | --- |
| 锁定段 | 被花费输出的版本 |
| 解锁段 | 与锁定段相同 |
| `GOTO` 目标 | 目标所在输出的版本 |
| `EMBED` 目标 | 目标所在输出的版本 |
| `EVAL` 代码 | 所执行的 Script 值携带的版本 |

Script 值的版本：

- `CODE` 创建的 Script，取 `CODE` 指令所在段的版本。
- `SCRIPT` 创建的 Script，取被引用输出的版本。创建时不检查该版本是否已知（检查在 `EVAL` 时进行，第 5 条）。

**每条指令按其所在段的版本解码和执行。** `EMBED` 的代码虽然在调用者的脚本域内执行，其中每条指令仍按嵌入段的版本处理。`CALL` 使用的方法集，取该 `CALL` 指令所在段的版本。

### 3. 一个版本冻结的内容

| 表 | v1 所在 |
| --- | --- |
| 指令码表：每个指令的附参格式、取值范围、附参是否属于索引类 | SPEC-0002 |
| 环境字段表：`GVAL`、`ENV`、`IN`、`OUT`、`INOUT`、`XFROM` | 核心字段见 SPEC-0008 第 3 条；宿主字段见宿主规格（Evidcoin：SPEC-0901〔P-08〕） |
| 见证条目表（系统占位符的附参） | 宿主规格〔P-08〕 |
| `FN_X`、`FN_XX`、`EXT_MO` 的索引表，哈希算法标识、MODEL 类型标识等其它索引类附参的取值表 | SPEC-0002（v1 中 `FN_X`、`FN_XX`、`EXT_MO` 没有已分配的条目）；MODEL 类型标识见 SPEC-0103〔P-07〕 |
| 各模块与系统对象的**静态方法表**：方法索引、索引别名、参数类型、返回类型、成本函数、公 / 私域标注 | SPEC-0105〔P-05〕 |
| 各模块与系统对象的 **`CALL` 方法集**：方法名、参数类型、返回类型、成本函数、公 / 私域标注 | SPEC-0105〔P-05〕 |
| 成本表与硬限额 | SPEC-0006〔P-02〕 |

**已分配的条目永不修改。** 未分配的条目可以在原版本内分配，规则见第 6 条。`CALL` 方法集例外：一个版本发布之后，其中任何模块或对象的 `CALL` 方法集都不再增减。

宿主指令（SPEC-0002 标记 H）：宿主规格没有实现的宿主指令，对该宿主而言是未分配码位（DEC-0002 第 1 条）。

### 4. 未分配与宽松通过

**未分配**是指：

- 当前版本没有分配的指令码，包括量子安全保留区 156–163 与构想层标为「未用」的码值；
- 索引类附参（SPEC-0002 中标注「**索引**」的附参）的未分配取值：环境字段的索引、见证条目的索引（系统占位符）、`FN_X` / `FN_XX` 的索引、`EXT_MO` 的模块索引与方法索引、模块的静态方法索引（例如 `MO_MATH{Abs}` 的附参）、哈希算法标识、MODEL 的类型标识等。

非索引类附参的取值越界是结构错误，不是未分配（SPEC-0003 第 3 条第 9 项）。

加载期（SPEC-0003 第 2.3 条）扫描到未分配时：

| 段 | 结论 |
| --- | --- |
| 锁定段、`GOTO` 目标、`EMBED` 目标（锁定方的段） | **宽松通过**：本次验证立即以「通过」结束，不再执行任何指令 |
| 解锁段 | 失败 |
| `EVAL` 代码 | 失败 |

规则：

1. **宽松通过的范围是整个验证**，不只是那一段。在 `GOTO` 目标或 `EMBED` 目标中宽松通过时，调用者的后续代码不再执行，调用者之前的状态（包括其通关状态）也不再影响结果。否则旧节点会回到调用者继续执行，而新节点执行了新语义，两边的后续结果可能不同。
2. 宽松通过在加载时判定，与该码位是否会被执行到无关：一段中任何位置出现未分配，只要它是该段的首个事件，就宽松通过。
3. 一段之内按字节顺序扫描，最先出现的事件（结构错误或未分配）决定该段的结论（SPEC-0003 第 2.3 条）；各段的加载顺序见 SPEC-0003 第 1、2 条。
4. 码值 255 永久保留，出现在任何段都是结构错误。码值 254（系统占位符）已分配，出现在解锁段以外（模式体除外）是结构错误（SPEC-0003 第 7 条）。
5. 私有专属指令（SPEC-0002 标记 P）是已分配码位，不宽松通过：公共验证执行到即失败（SPEC-0005 第 10 条）。
6. **`CALL` 严格，静态方法宽松。** `CALL` 的方法名是运行时的字符串，加载期看不到，不适用宽松通过：调用 `CALL` 指令所在段的版本的 `CALL` 方法集中没有的方法，即失败。以附参索引调用的静态方法（模块，以及系统对象：Time 对应 `MO_TIME`，RegExp 对应 `MO_RE`，扩展模块对应 `EXT_MO`）在加载期可见，未分配的静态方法索引按本条处理。

### 5. 未知版本

| 情形 | 结论 | 时点 |
| --- | --- | --- |
| 锁定段的版本未知 | 宽松通过，不再加载任何段（包括解锁段） | 验证开始时（SPEC-0003 第 2.1 条） |
| `GOTO` / `EMBED` 目标的版本未知 | 宽松通过 | 加载该目标时 |
| `EVAL` 代码的版本高于发起 `EVAL` 的段的版本（含未知版本） | 失败 | 执行 `EVAL` 时，加载代码之前 |

- 「发起 `EVAL` 的段」是 `EVAL` 指令所在的段，例如 `EVAL` 写在 `EMBED` 目标中，比较的对象就是该 `EMBED` 目标的版本。
- EVAL 的规则在新旧节点上都判失败，因此不会分叉。宽松通过不能用于 EVAL：解锁段可以用 `SCRIPT` 引用任何已上链的输出，包括使用了未知版本的输出；如果 EVAL 遇到未知版本判通过，锁定脚本对 EVAL 结果的检查就被绕过了（DEC-0004 理由）。

### 6. 升级规则

本条约束规格的维护者：每一次变更都必须属于下表的一行。

| 变更 | 在原版本内 | 条件 |
| --- | --- | --- |
| 给未分配的指令码或索引取值赋义 | 可以（软分叉） | 新语义只在锁定方的段中生效；在解锁段与 EVAL 代码中，该码位在原版本下仍按未分配处理（失败） |
| 给已有模块或系统对象增加方法 | 可以，只能作为静态方法（软分叉） | 分配一个静态方法索引，按上一行处理 |
| 新分配一个模块（如 `EXT_MO` 的模块索引） | 可以（软分叉） | 随分配一起给出它的静态方法表与 `CALL` 方法集，之后冻结；生效范围按第一行 |
| 向已发布的 `CALL` 方法集增加方法 | 不可以 | 发布新版本 |
| 新码位在解锁段或 EVAL 代码中生效 | 不可以 | 发布新版本 |
| 修改已分配条目的语义、格式或成本 | 不可以 | 发布新版本 |
| 调整成本表或硬限额 | 不可以 | 发布新版本（DEC-0004 第 2 条） |

由此，原版本内软分叉加入的条目带有一个**生效范围**：只在锁定方的段中生效。版本表必须为每个条目记录它的生效范围（全部段，或只在锁定方的段）。v1 发布时的全部条目，生效范围都是全部段。

软分叉加入的条目在激活之前按未分配处理。激活机制由宿主规格定义〔P-04〕。

新模块的 `CALL` 调用不会引起分歧：该模块的对象只能由锁定方段中的构造指令产生，而旧节点在加载该段时已经宽松通过。EVAL 环境不接收外部的值（SPEC-0005 第 11.3 条），因此这类对象也不会进入 EVAL 代码。

一个新方法的典型路径：先在当前版本中作为静态方法以软分叉加入；下一个版本发布时，再进入该版本的 `CALL` 方法集。

### 7. 转发策略（非共识）

节点**不应**转发或打包这样的交易：它创建的输出，其锁定脚本含有未分配码位（按本节点所知的该版本的表），或使用了本节点不认识的版本。这可以防止有人误把资金锁进实际上任何人都能花费的脚本（DEC-0004 第 6 条）。

### 8. v1

v1 的各张表分布在：SPEC-0002（指令码表、索引类附参）、SPEC-0105（方法表〔P-05〕）、SPEC-0006（成本表与硬限额〔P-02〕）、SPEC-0008 第 3 条（核心环境字段）、宿主规格（宿主字段表、见证条目表）。全部待决项决定并通过校准之后，v1 冻结。


## 边界与限制

- 软分叉的激活使同一笔交易的有效性随区块高度变化。激活前后的内存池重验由宿主处理，不属于核心。
- 版本号不放进字节码，因此字节码本身不能自述版本。编译器、反编译器与测试向量必须显式携带版本（SPEC-0201、0202）。
- 本篇不规定新版本的发布流程，只规定哪些变更必须通过新版本。

## 对 Plan 的约束

- 版本表必须是数据驱动的：按版本索引的指令码表、索引表、方法表、成本表。每个条目记录生效范围与激活条件。不得用散落在代码中的 `if version >= N` 实现版本差异。
- Script 值的内部表示必须携带版本号。
- 解码器必须以「段的种类 + 版本」为输入，输出加载结论（成功、失败、宽松通过）。
- 测试向量必须覆盖（DEC-0004 影响一节）：锁定段、`GOTO` 目标、`EMBED` 目标、解锁段、EVAL 代码中分别出现未分配码位；未分配的静态方法索引；`CALL` 调用未知方法；EVAL 代码的版本高于调用段；锁定段的版本未知；`GOTO` 目标宽松通过时调用者的通关状态为未通过。
