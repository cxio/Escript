## 规格正文

### 1. 版本字段

Evidcoin 有三个版本号（`Design.md`「附：版本关系」）：

| 位置 | 长度 | 说明 |
| --- | --- | --- |
| 区块头 | 4 字节 | 区块版本 |
| 交易头 | 2 字节 | bit15 为预发布标记，低 15 位为交易版本号（第 2 条） |
| 输出项配置的首字节 | 1 字节 | 输出项版本，即脚本版本 |

- 核心取用的是输出项版本（SPEC-0007 第 1 条）。v1 对应的取值〔P-09〕；其余取值都是未知版本。
- 下级版本变更连带上级版本更新：引入新的脚本版本的同时，交易版本与区块版本也递增。旧版区块不能收录新版交易（`Design.md`「附：分叉种类」）。交易版本与区块版本的规则由 Evidcoin 的交易与区块规格给出。
- 区块版本、交易版本不进入核心。核心只按输出项版本加载和执行脚本。

### 2. 新版本的接受：预发布〔R-34、R-35〕

新的脚本版本只能随新的交易版本一起发布，并经过预发布才生效（SPEC-0007 第 6 条）。

#### 2.1 交易头的版本字段

- 2 字节，bit15 是预发布标记 F，低 15 位是交易版本号 T。
- **F 不影响交易的有效性**〔R-35〕：交易按 T 验证，F 只用于统计。因此从第一个版本起，节点就必须按低 15 位识别交易版本，并接受 F = 1 的交易；否则预发布期间置标的交易会被尚未升级的节点拒绝。
- 预发布期间，支持新版的用户发出 T 为当前版本、F = 1 的交易，表示「新版已经出来，版本号将加 1」。

#### 2.2 一次预发布

新版客户端发布时给出以下参数，它们属于该客户端版本的共识参数：

| 参数 | 说明 |
| --- | --- |
| 新的交易版本 | T + 1，T 为当前版本；连带引入的脚本版本（如有）与区块版本 |
| 截止高度 H | 由「生效时间」折算的区块高度（构想层的例子是 3 个月之后），须高于发布时的链高度 |
| 阈值 n / d | 正整数，n ≤ d（构想层的例子是 60 / 100） |

- 同一时刻至多有一个进行中的预发布〔R-35〕：上一次预发布生效或作废之前，不发布下一次。
- 高度 H 之前，F 只用于观察，不参与判定。

#### 2.3 统计与判定〔R-34〕

**统计窗口**是高度 H 至 H + 4 的 5 个区块（`Design.md`：「由截止高度区块及之后 4 个区块的铸造者……实施阻止」）。

```
new   = 窗口内 F = 1 的交易数
total = 窗口内的交易数
生效  ⇔  total > 0  且  new × d ≥ total × n
```

- 两个计数都不含 Coinbase 交易。Coinbase 的版本由铸造者填写，铸造者对升级的影响通过「选择收录哪些交易」实现（`Design.md`「撤回机制」）。
- total = 0 时不生效。按公式 0 ≥ 0 会判为生效，但窗口内没有任何交易，不能说明新版被采用。
- 乘法按任意精度整数计算，不会溢出。
- 判定在高度 H + 4 的区块确定之后进行，只取决于本链上这 5 个区块的内容。链重组时按新链重新判定。
- 统计与判定不计入任何交易或区块的脚本成本（DEC-0004 第 5 条）。

#### 2.4 结果

| 结果 | 规则 |
| --- | --- |
| 生效 | 从高度 **H + 5** 起（含）接受版本 T + 1 的交易，以及使用新脚本版本的输出。此后新版交易的 F 为 0，低 15 位为 T + 1 |
| 未达阈值 | 本次升级作废：不接受版本 T + 1，链继续使用版本 T。再次升级需要新的预发布（新的 H） |

- 生效之后，版本 T 的交易（F 为 0 或 1）仍然有效（`Design.md`：「旧版本 + 预发布置标的旧版交易依然有效」；新增版本是弱分叉，SPEC-0007 第 6 条）。
- 脚本版本 v 在高度 h **已生效**，是指：v = v1（自创世区块起），或引入 v 的那次预发布已生效且 h ≥ H + 5。创建输出时检查这一点（第 9 条）。
- 没有升级的节点不认识 T + 1 与新脚本版本，按 SPEC-0007 第 5 条与本条拒绝它们，新旧分叉由分叉竞争决出（`Design.md`「未知码位处理」）。

### 3. 环境字段表〔P-08〕

本条的索引、名称与类型是起草稿，待作者确认。各表的列：

- **类型**：SPEC-0004 的值类型。宿主不提供 Float（SPEC-0008 第 4 条）。
- **源码类**：是，则单项上限 16384 字节，否则 8191 字节（SPEC-0006 第 1 条）。
- **高度**：是，则读取时设置「高度相关」执行标记（SPEC-0008 第 6 条）。
- **取不到**：字段在该交易中不适用时的结果。「Nil」表示返回 Nil；「不可用」表示节点暂时缺少数据，本次验证的结果为数据不可用。没有写的，总能取到。

时间戳都是 Unix 毫秒，类型为 Int（构想层「Unix 时间戳，毫秒」）；需要 Time 时用 `TIME` 转换。公钥哈希、交易 ID 等为 Bytes。

#### 3.1 `GVAL`

| 索引 | 名称 | 类型 | 说明 | 高度 |
| --- | --- | --- | --- | --- |
| 0 | `Height` | Int | 当前区块的高度，同 `ENV{Height}` | 是 |
| 1 | `TxID` | Bytes(48) | 当前交易的 ID，同 `ENV{TxID}` | |
| 2 | `OutKind` | Int | 同 `ENV{OutKind}` | |

`GVAL` 可以在解锁段使用（SPEC-0002 标记 U）。构想层示例 `GVAL[2]` 假设 `OutKind` 的索引为 2，与本表一致。

#### 3.2 `ENV` 的宿主字段

核心字段 0–9 见 SPEC-0008 第 3 条，10–31 归核心未分配。宿主字段：

| 索引 | 名称 | 类型 | 说明 | 高度 |
| --- | --- | --- | --- | --- |
| 32 | `BlockTime` | Int | 当前区块的时间戳。Evidcoin 的区块时间按固定的 6 分钟间隔由高度确定，因此是确定性的 | 是 |
| 33 | `Height` | Int | 当前区块的高度，即交易将进入的区块，`TipHeight + 1` | 是 |
| 34 | `TipHeight` | Int | 验证时链末端已确认区块的高度 | 是 |
| 35 | `TxID` | Bytes(48) | 当前交易的 ID | |
| 36 | `TxTime` | Int | 当前交易的时间戳 | |
| 37 | `OutKind` | Int | 被花费输出的类别：1 币金，2 凭信，3 存证〔R-36〕 | |

「当前交易」是正在验证的交易；在 `GOTO` / `EMBED` 目标中也是它（目标只提供代码）。`OutKind` 属于校验域，`GOTO` 链中取值相同。

#### 3.3 `IN`

当前输入及其来源输出（构想层：「站在锁定脚本源的位置，即未来被花费时输入部分的信息」）。

| 索引 | 名称 | 类型 | 说明 | 源码类 | 取不到 |
| --- | --- | --- | --- | --- | --- |
| 0 | `Timestamp` | Int | 来源交易的时间戳 | | |
| 1 | `TxID` | Bytes(48) | 来源交易的 ID | | |
| 2 | `Height` | Int | 来源交易所在区块的高度 | | |
| 3 | `Amount` | Int | 来源输出的币金数量 | | 凭信：Nil |
| 4 | `Receiver` | Bytes | 来源输出的接收者（公钥哈希） | | |
| 5 | `Remarks` | Bytes | 来源输出的附言 | | 没有附言：Nil |
| 6 | `Locked` | Bytes | 被花费输出的锁定脚本 | 是 | |
| 7 | `Unlock` | Bytes | 解锁脚本，含系统占位符的原始字节，不含见证信息 | 是 | |
| 8 | `Source` | Bytes | 解锁脚本与锁定脚本首尾相接，不含见证信息 | 是 | |
| 9 | `Index` | Int | 本输入在输入集中的序位，从 0 开始 | | |
| 10 | `Creator` | Bytes | 凭信的创建者 | | 币金：Nil |
| 11 | `Title` | String | 凭信的标题 | | 币金：Nil |
| 12 | `Description` | String | 凭信的描述 | | 币金：Nil |
| 13 | `Lifespan` | Int | 凭信的有效期，区块数 | | 币金：Nil |
| 14 | `Attachment` | Bytes | 附件 ID | | 没有附件：Nil |

节点验证一个输入时必然持有其来源输出，因此 `IN` 的字段不会数据不可用。

#### 3.4 `OUT` 与 `INOUT`

`OUT[n, i]` 取当前交易的第 n 个输出，`INOUT[n, i]` 取当前输入的来源交易的第 n 个输出。两者的字段相同：

| 索引 | 名称 | 类型 | 说明 | 源码类 | 取不到 |
| --- | --- | --- | --- | --- | --- |
| 0 | `Amount` | Int | 币金数量 | | 凭信、存证：Nil |
| 1 | `Receiver` | Bytes | 接收者 | | 没有接收者：Nil |
| 2 | `Remarks` | Bytes | 附言 | | 没有附言：Nil |
| 3 | `Creator` | Bytes | 凭信、存证的创建者 | | 币金：Nil |
| 4 | `Title` | String | 凭信、存证的标题 | | 币金：Nil |
| 5 | `Description` | String | 凭信的描述 | | 币金、存证：Nil |
| 6 | `Content` | Bytes | 存证的内容 | | 币金、凭信：Nil |
| 7 | `Attachment` | Bytes | 附件 ID | | 没有附件：Nil |
| 8 | `Locked` | Bytes | 输出的锁定脚本 | 是 | |

- n 不小于输出集的大小即失败（按位置，SPEC-0104 第 2.1 条）。
- `INOUT` 需要来源交易的其它输出。节点缺少这些数据、交易也没有携带验证上下文时，结果为数据不可用（构想层 `AGENTS.md`）。

#### 3.5 `XFROM`

只能在 `GOTO` / `EMBED` 目标中使用（SPEC-0104 第 2.2 条）。「源交易」是正在验证的交易，「源脚本」是正在验证的输入的锁定脚本，即顶层的锁定段〔R-36〕。

| 索引 | 名称 | 类型 | 说明 | 源码类 |
| --- | --- | --- | --- | --- |
| 0 | `InSize` | Int | 源交易的输入数 | |
| 1 | `InAmount` | Int | 源交易全部币金输入的金额之和 | |
| 2 | `OutSize` | Int | 源交易的输出数 | |
| 3 | `OutAmount` | Int | 源交易全部币金输出的金额之和 | |
| 4 | `Account` | Bytes | 源脚本的账户：被花费输出的接收者（公钥哈希） | |
| 5 | `Amount` | Int | 被花费输出的币金数量；凭信为 Nil | |
| 6 | `PayKind` | Int | 被花费输出的类别，取值同 `ENV{OutKind}` | |
| 7 | `Locked` | Bytes | 源脚本 | 是 |
| 8 | `Source` | Bytes | 源脚本从开头到跳转点：`[0, p)`，p 为顶层锁定段中当前 `GOTO` 链起点那条 `GOTO` 或 `EMBED` 指令之后的位置 | 是 |
| 9 | `Timestamp` | Int | 源交易的时间戳 | |

- 暂不提供解锁段的信息（构想层：「解锁信息应当由当前脚本处理，不对外泄露」）。
- `Source` 的跳转点〔R-36〕：`GOTO` 目标中再 `GOTO` 或 `EMBED` 时，跳转点仍是顶层锁定段中的那一条，与 `SOURCE` 的「前阶含本指令」一致。

### 4. 见证条目表〔P-08〕

#### 4.1 见证信息

见证信息随交易的输入提供，导入环境，不进入数据栈（`Design.md`「例：币金支付验证」）。逻辑上包含：

| 项 | 类型 | 说明 |
| --- | --- | --- |
| 签名类别 | 1 或 2 | 1 单签，2 多签 |
| 授权标识 | Byte | 标准验证用；定制验证中授权标识写在解锁脚本里（DEC-0002 第 2 条） |
| 签名集 | Bytes 的序列 | 单签恰好 1 个 |
| 公钥集 | Bytes 的序列 | 与签名集一一对应 |
| 补全集 | Bytes 的序列 | 多签：未参与签名的公钥的初级哈希，每个 32 字节 |

见证信息的编码属于 Evidcoin 的交易格式。它不计入解锁脚本的长度（`Design.md`「参数限定」），不参与 TxID（DEC-0002「影响」）。

#### 4.2 系统占位符的附参

| 索引 | 名称 | 类型 | 取值 | 存在条件 |
| --- | --- | --- | --- | --- |
| 0 | `<Sig>` | Bytes | 签名集的唯一成员 | 签名类别为 1 |
| 1 | `<PubKey>` | Bytes | 公钥集的唯一成员 | 签名类别为 1 |
| 2 | `<Sigs>` | `[]Bytes` | 签名集 | 签名类别为 2 |
| 3 | `<PubKeys>` | `[]Bytes` | 公钥集 | 签名类别为 2 |
| 4 | `<Rests>` | `[]Bytes` | 补全集，可以为空 | 签名类别为 2 |

- 不满足存在条件，执行到该占位符即失败（SPEC-0005 第 13 条）。
- 取用时按 SPEC-0006 第 1 条检查单项大小与集合成员数。
- 没有授权标识的占位符（构想层）。

### 5. 外部脚本引用

#### 5.1 引用字段

`GOTO`、`EMBED`、`SCRIPT` 的 `HostRef`（SPEC-0002 第 2.2 条〔R-04〕）：

| 序号 | 类型 | 含义 |
| --- | --- | --- |
| 1 | `uvarint` | 年度：目标交易时间戳所在的公历年，按 UTC 计〔R-37〕 |
| 2 | `bytes(48)` | 目标交易的 ID |
| 3 | `uvarint` | 目标输出在该交易输出集中的序位，从 0 开始 |

目标是该输出的锁定脚本，版本是该输出的输出项版本（第 1 条）。任何类别的输出都可以作为目标（存证常用于介管脚本定义），已花费与否不影响。

#### 5.2 取数〔R-37〕

| 情形 | 结果（SPEC-0008 第 5.1 条） |
| --- | --- |
| 目标交易在当前区块之前的区块中，输出序位有效 | 字节码与版本 |
| 拥有完整历史索引的节点查不到该交易；或年度与该交易不符；或序位不小于其输出数 | 不存在：失败 |
| 节点缺少相应的历史数据，交易也没有携带有效的验证上下文 | 数据不可用 |

- 目标必须位于当前区块之前已确认的区块中。同一区块或内存池中的交易不是可引用的目标。
- 交易可以携带验证上下文：目标输出及其默克尔路径（构想层 `AGENTS.md`；输出项内容与脚本超过 64 字节时以摘要参与计算，见 `Evidcoin设计参考.md`「配置/状态」）。宿主验证路径到本节点已有的区块头。路径无效时按没有携带处理，结果只取决于节点自己的数据。
- 成本按 SPEC-0006 第 3 条的外部加载计，与上下文的来源无关。

### 6. 签名验证

#### 6.1 签名算法

签名算法与公钥、签名的格式由 Evidcoin 的密码学规格选定〔P-03〕。本篇只规定验证的输入输出：`Verify(pubKey, msg, sig)` 返回成功或不成功。公钥或签名的格式不符合算法要求，按「不成功」处理，不是失败。

#### 6.2 授权标识与签名消息

授权标识是 1 个字节（`Evidcoin设计参考.md`「授权种类」）：

| 位 | 名称 | 类别 | 签名消息包含 |
| --- | --- | --- | --- |
| 7 | `SIGIN_ALL` | 独项 | 全部输入，含各自的解锁脚本，不含见证信息 |
| 6 | `SIGIN_SELF` | 独项 | 当前输入，含其解锁脚本，不含见证信息 |
| 5 | `SIGOUT_ALL` | 主项 | 全部输出中由辅项选定的部分 |
| 4 | `SIGOUT_SELF` | 主项 | 与当前输入同序位的输出中由辅项选定的部分 |
| 3 | `SCRIPT` | 辅项 | 输出的锁定脚本 |
| 2 | `CONTENT` | 辅项 | 输出的内容：除脚本与接收者之外的全部条目 |
| 1 | `RECEIVER` | 辅项 | 输出的接收者 |
| 0 | `OUTPUT` | 辅项 | 输出的全部（脚本、内容与接收者） |

**合法的授权标识**〔R-38〕同时满足：

1. 不为 0；
2. 主项（bit5、bit4）不为 0，当且仅当辅项（bit3–bit0）不为 0；
3. bit0 置位时，bit3–bit1 都为 0（`OUTPUT` 与 `SCRIPT`、`CONTENT`、`RECEIVER` 互斥）。

授权标识不合法，或 `SIGOUT_SELF` 置位而当前输入的序位没有对应的输出，签名验证指令即失败（不是「不成功」）〔R-38〕。

**签名消息**由以下部分组成：交易头的版本字段（含预发布标记）、交易时间戳、铸凭公钥哈希（如有）、授权标识本身，以及授权标识选定的输入与输出部分（`Evidcoin设计参考.md`「提示」）。

- 「当前输入」是正在验证的输入；签名验证指令位于 `GOTO` / `EMBED` 目标中时也是它。
- 解锁脚本以含系统占位符的原始字节参与签名消息（`Design.md`「附：系统占位符」），因此签名不依赖自身。
- 各部分的字节序列化与拼接顺序，属于 Evidcoin 的交易规格。
- Coinbase 交易对整个交易签名，不使用授权标识，与脚本无关。

#### 6.3 多签的公钥清单〔R-39〕

多签的 N 个参与者按以下规则排成一个清单，复合公钥哈希与校验域的序位都以它为准：

1. 每个参与签名的公钥，计算初级哈希 `BLAKE3-256(pubKey)`（32 字节）；补全集的成员就是初级哈希，必须恰好 32 字节。
2. 把 N 个初级哈希按字节的字典序升序排列，得到清单 `L[0] … L[N-1]`。清单中有相同的成员即失败。
3. m 为签名数，N = m + 补全集的成员数，要求 1 ≤ m ≤ N ≤ 255。
4. 复合公钥哈希 `MixPKH = SHA3-256( byte(m) ‖ byte(N) ‖ BLAKE2b-512( L[0] ‖ … ‖ L[N-1] ) )`。

序位 i 对应清单成员 `L[i]`（构想层 `SIGNED`：「多重签名公钥哈希清单中的序位，从 0 开始」）。

#### 6.4 `SYS_CHKPASS`

没有实参，从见证信息取得签名类别、授权标识、签名集、公钥集与补全集（构想层声明 `SYS_CHKPASS(花费者, 签名类别, 授权标记, []签名, []公钥, []初级哈希)`）。花费者是当前输入的来源输出的接收者（`IN{Receiver}`）。

| 签名类别 | 验证 | 成功时写入校验域 |
| --- | --- | --- |
| 1 | 签名集与公钥集各恰好 1 个；`FN_PUBHASH(pubKey)` 等于花费者；签名验证成功 | 序位 0 为 true |
| 2 | 按第 6.3 条得到清单与 `MixPKH`，`MixPKH` 等于花费者；签名集与公钥集个数相同；每个签名都验证成功 | 签名者的序位为 true，补全集成员的序位为 false |

- 见证信息缺少所需的项、签名类别不是 1 或 2、授权标识不合法、任一检查不成立，都是 `SYS_CHKPASS` 失败：否决，本次验证失败（SPEC-0104 第 4 条）。
- 成功：当前脚本域置为「通过」，按上表写入校验域（SPEC-0008 第 5.2 条）。
- 在 EVAL 代码中出现即加载失败（SPEC-0003）。
- 超级赎回不在本篇范围内（DEC-0002 开放问题 1）。

#### 6.5 `FN_CHECKSIG`、`FN_MCHECKSIG`

用于定制验证。它们只验证签名，不核对花费者地址；地址由脚本自己核对（`Design.md`「例：定制验证」）。

| 指令 | 实参 | 验证 | 写入校验域（EVAL 中不写） |
| --- | --- | --- | --- |
| `FN_CHECKSIG` | 授权标识 Byte，签名 Bytes，公钥 Bytes | 签名验证 | 序位 0 为验证结果 |
| `FN_MCHECKSIG` | 授权标识 Byte，签名集，公钥集，补全集 | 按第 6.3 条排出清单；逐个验证全部签名 | 签名者的序位为其签名的验证结果，补全集成员的序位为 false |

- 签名集、公钥集、补全集为 `[]Bytes`，或成员全为 Bytes 的 `[]any`。
- 返回 Bool：`FN_CHECKSIG` 为验证结果；`FN_MCHECKSIG` 在每个签名都验证成功时为 true。验证不成功不是失败。
- 失败情形：实参类型不符（授权标识为 Byte 以外的类型，包括 Int）；授权标识不合法（第 6.2 条）；`FN_MCHECKSIG` 的签名集与公钥集个数不同或为空，或违反第 6.3 条第 1–3 项。
- `FN_MCHECKSIG` 即使已有签名不成功，也验证全部签名，以便写入每个序位。它的成本在调用之前按签名数确定（第 6.6 条）。

#### 6.6 成本〔P-03〕

记 `S` 为一次签名验证的成本，`h(算法, x)` 为对 x 字节计算该哈希的成本 `20 + B(x) × k`（k 见 SPEC-0006 第 3 条）。以下为校准起点：

| 指令 | 成本 |
| --- | --- |
| `SYS_CHKPASS` 单签 | `K + S + h(BLAKE2b-512, 公钥字节) + h(SHA3-256, 64)` |
| `SYS_CHKPASS` 多签 | `K + N + m × S + Σ h(BLAKE3, 公钥字节) + h(BLAKE2b-512, 32N) + h(SHA3-256, 66)` |
| `FN_CHECKSIG` | `K + S` |
| `FN_MCHECKSIG` | `K + N + m × S + Σ h(BLAKE3, 公钥字节)` |

- `S` 的起点为 1000（DEC-0007：「量级约 1000」），随签名算法校准。
- `SYS_CHKPASS` 的 a、r 都为 0，`K` 为 1。
- 成本在调用宿主之前计入（SPEC-0008 第 5 条），只取决于实参或见证信息的个数与长度。

### 7. 公钥哈希与地址

| 指令 | 实参 | 返回 | 成本〔P-03〕 |
| --- | --- | --- | --- |
| `FN_PUBHASH` | 公钥，Bytes | `SHA3-256(BLAKE2b-512(pubKey))`，Bytes(32) | `K + h(BLAKE2b-512, 公钥字节) + h(SHA3-256, 64)` |
| `FN_MPUBHASH` | 初级哈希集，`[]Bytes` 或成员全为 Bytes 的 `[]any`；m；N | 第 6.3 条的 `MixPKH`，Bytes(32) | `K + N + h(BLAKE2b-512, 32N) + h(SHA3-256, 66)` |
| `FN_ADDRESS` | 见 7.1 | 见 7.1 | `K + 10` |

- `FN_PUBHASH`：实参不是 Bytes 即失败。
- `FN_MPUBHASH`：m、N 是整数类实参（SPEC-0101 第 1.2 条）；初级哈希集的成员数必须等于 N；其余按第 6.3 条（每个成员 32 字节、无重复、1 ≤ m ≤ N ≤ 255），不满足即失败。

#### 7.1 `FN_ADDRESS`：Bech32v〔R-40〕

Bech32v 在 Bech32m（BIP 350）之上，把数据部分的字符按「视觉字母表」改写大小写（构想层 `16.函数指令.md`）：

```
计算字符集：qpzry9x8gf2tvdw0s3jn54khce6mua7l
视觉字母表：qPzRy9x8Gf2TvDw0s3jN54kHcE6MUA7L
```

两者逐位对应，视觉字母表就是把计算字符集中的 `p r g t d n h e m u a l` 改为大写。

**编码**：实参 1 为 Bytes（公钥哈希），实参 2 为 String（HRP）。

1. HRP 为 1–83 个字符，每个字符在 ASCII 33–126 之内，否则失败；大写字母转为小写。
2. 按 BIP 173 把数据从 8 位分组转为 5 位分组（末组补 0），按 BIP 350 计算 Bech32m 校验和，得到全小写的 `hrp ‖ "1" ‖ 数据部分`。
3. 把分隔符之后的每个字符替换为视觉字母表中的对应字符。HRP 不改写。
4. 结果超过 90 个字符即失败。返回 String。

**解码**：实参 1 为 String（地址），实参 2 为 Nil 或 String，忽略其值（构想层：「解码时前缀省略，调用者传递 nil 占位」）。

1. 长度超过 90 个字符即失败。全部转为小写（不区分大小写）。
2. 按 BIP 173 / 350 解码：以最后一个 `1` 为分隔符，HRP 1–83 个字符，数据部分至少 6 个字符且都在计算字符集中，Bech32m 校验和正确；5 位分组转回 8 位分组时，补位不超过 4 位且全为 0。不满足即失败。
3. 返回数据部分（去掉校验和）还原的 Bytes。

- 实参 1 为其它类型、编码时实参 2 不是 String，即失败。
- 解码结果与 HRP 无关，所以不同 HRP 的同一公钥哈希解码相同。比较地址文本时应按不区分大小写进行。

### 8. `SYS_AWARD`（兑奖验算）

附参：`u8` 输出序位，`u32be` 区块高度（SPEC-0002）。没有实参，返回 Bool。

- **只用于 Coinbase 交易的输出脚本**。本篇规定〔R-41〕：
  - 创建时（第 9 条）：Coinbase 输出的锁定脚本中，每一条 `SYS_AWARD` 的附参 1 等于该输出的序位、附参 2 等于该 Coinbase 所在区块的高度，否则交易无效（构想层：「此规则在 Coinbase 交易合法性检查时核实」）。
  - 执行时：只有位于顶层锁定段、且被花费的输出属于 Coinbase 交易时才执行验算；位于其它段（`GOTO` / `EMBED` 目标、EVAL 代码），或被花费的输出不属于 Coinbase 交易，即失败。
- 验算：按附参 2 之后的链段与兑奖槽情况计算兑奖比例（0、50、100），按比例核算花费的金额是否合法，返回结果；比例为 0 时返回 false（构想层）。兑奖槽、比例与可用金额的计算属于 Evidcoin 的兑奖规则〔P-10〕。
- 结果取决于附参 2 之后的链段，因此执行 `SYS_AWARD` 设置「高度相关」执行标记。
- 成本：`K + 100`〔P-03〕。

### 9. 创建输出时的检查

Evidcoin 把 DEC-0004 第 5 条的检查定为**共识规则**。交易（包括 Coinbase）进入区块时，对它的每个输出依次检查，任一项不满足，交易无效：

1. 锁定脚本的长度小于 8192 字节（SPEC-0006 第 1 条）。
2. 输出项版本映射到一个核心版本（第 1 条），且该版本在交易所在区块的高度已生效（第 2.4 条）。
3. 调用核心的创建时检查（SPEC-0008 第 5.4 条）：按该版本把锁定脚本作为锁定段加载，不执行。
4. Coinbase 输出另须满足第 8 条对 `SYS_AWARD` 附参的要求。

内存池中的交易按「下一个区块的高度」检查第 2 项。

### 10. 参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `MaxInputScriptCost` | 500,000（沿用核心默认值） | SPEC-0006 第 4 条 |
| `MaxTxScriptCost` | 5,000,000（沿用核心默认值） | 同上 |
| `MaxBlockScriptCost` | 4,000,000,000 | DEC-0007 第 4 条 |
| 出块间隔 | 6 分钟，每天 240 个区块 | DEC-0002 第 2 条 |
| 锁定脚本 / 解锁脚本 | 各小于 8192 字节；解锁脚本不含见证信息 | `Design.md`「参数限定」 |
| 凭信的描述、存证的内容 | 小于 2048 字节 | `Design.md`「参数限定」 |

**成本的累计**〔R-42〕：

```
交易的脚本成本 = Σ 各输入验证的实际成本 + Σ 各输出创建时检查的加载期成本
区块的脚本成本 = Σ 区块中各交易的脚本成本
```

- 交易的脚本成本不超过 `MaxTxScriptCost`，区块的脚本成本不超过 `MaxBlockScriptCost`，否则无效。Coinbase 交易只有第二项。
- 创建时检查的成本计入交易成本（DEC-0004 第 5 条）；预发布的版本位检查与统计不计入（第 2.3 条）。
- 区块预算的前提（DEC-0007）：40 亿单位约为单核 400 秒，超过 6 分钟的出块间隔。它依赖两点：不同输入之间并行验证（8 核约 50 秒）；Evidcoin 采用组队校验，每个节点只验证区块中的一部分交易。

**执行结果的处理**按 SPEC-0008 第 6 条。顶层 `EXIT` 的实参在 Evidcoin 中没有用途，忽略。

### 11. 本地输出与私有域〔P-08〕

Evidcoin 没有额外的私有域规则。节点按 SPEC-0008 第 7 条与 SPEC-0106 提供本地输出与私有通道；`SHELL` 的开关默认关闭，公共节点与私有节点相同。

**`SHELL` 的来源输出数据**（SPEC-0104 第 3.12 条）。来源输出是当前输入所花费的输出，即第 3.3 条 `IN` 所描述的那一项；在 `GOTO` / `EMBED` 目标与 EVAL 代码中不变。宿主按下表的顺序给出全部字段，与输出类别无关的字段为 Nil：

| 序 | 名称 | 类型 | 取值 |
| --- | --- | --- | --- |
| 0 | `TxID` | Bytes(48) | 当前交易的 ID，同 `ENV{TxID}`（供执行器去重） |
| 1 | `Index` | Int | 当前输入在输入集中的序位，同 `IN{Index}` |
| 2 | `OutKind` | Int | 来源输出的类别：1 币金，2 凭信，3 存证，同 `ENV{OutKind}` |
| 3 | `Receiver` | Bytes | 来源输出的接收者（公钥哈希），同 `IN{Receiver}` |
| 4 | `Amount` | Int | 币金数量；凭信、存证为 Nil |
| 5 | `Remarks` | Bytes | 附言；没有附言为 Nil |
| 6 | `Creator` | Bytes | 凭信、存证的创建者；币金为 Nil |
| 7 | `Title` | String | 凭信、存证的标题；币金为 Nil |
| 8 | `Description` | String | 凭信的描述；币金、存证为 Nil |
| 9 | `Lifespan` | Int | 凭信的有效期，区块数；币金、存证为 Nil |
| 10 | `Content` | Bytes | 存证的内容；币金、凭信为 Nil |
| 11 | `Attachment` | Bytes | 附件 ID；没有附件为 Nil |

- 构想层写作「接收者公钥」。输出中保存的是接收者的公钥哈希，公钥只在花费时随见证信息出现，定制验证中也可能没有，因此这里给出公钥哈希。
- 字段 4–11 取自来源输出本身，与第 3.3、3.4 条同名字段的取值相同。本表与第 3 条一样是起草稿〔P-08〕。
- 数据传给执行器时的编码（例如环境变量、JSON）属于节点的实现，不在本篇规定。

- `Evidcoin设计参考.md`「安全检查」把「不认识的版本号不收录不转发」写作共约。DEC-0004 第 5 条（作者 2026-11-12 修订）已改为共识检查，本篇按 DEC-0004。

## 对 Plan 的约束

- Evidcoin 宿主实现为独立的包，实现 SPEC-0008 的接口；核心包不引用它。字段表、见证条目表、授权标识的合法性、预发布参数都实现为数据表。
- 预发布的状态（进行中、已生效及其高度、已作废）从链上数据推导，不保存为节点的本地设置；必须有链重组跨越 H + 4 的测试。
- 测试向量（宿主部分，SPEC-0202）至少覆盖：
  - 预发布：恰好达到阈值、差 1 笔未达、窗口内只有 Coinbase（total = 0）、生效前后在 H + 4 与 H + 5 创建新版本输出、生效后版本 T 置标交易仍有效；
  - 授权标识：每一条合法性规则的违反；`SIGOUT_SELF` 没有同序位输出；
  - 多签：清单排序、重复成员、m = N、N = 255、补全集为空、成员不是 32 字节；`SIGNED` 的序位与写入值；
  - `FN_ADDRESS`：BIP 350 的有效与无效向量（按 Bech32v 改写大小写）、大小写混合输入、超长、补位非零；
  - 外部引用：存在、不存在（三种情形）、数据不可用、无效的验证上下文；
  - 创建时检查：每一项不满足；检查成本计入交易成本并触发 `MaxTxScriptCost`；
  - `SHELL` 的来源输出数据：三种输出类别各一例，以及 `SHELL` 位于 `GOTO` 目标中时字段仍取被花费的输出。
