# DEC-0007 资源限额与成本模型

- 状态：Accepted
- 日期：2026-10-28
- 修订：2026-11-01（采纳作者的预算提议；明确预算的配置层级）；2026-11-04（预算调整的分叉种类改按弱分叉、强分叉表述）；2026-11-08（`FN_BASE58` 编码限制实参、解码限制结果，均为 256 字节）；2026-11-18（作者增补提议：成本额度与交易费挂钩，基础预算之外可由交易购买增量额度，另设单输入、单交易的硬上限；第 2、4、5、6 条相应修订）
- 覆盖评审条目：P0-7（Q8、Q15，以及作者在 P0-7 中的三项提议）；作者增补提议（2026-11-18，`Design.md#交易费因子`）


## 背景

区块链是开放系统，攻击者可以构造极其消耗资源的交易。构想层已经有一组硬限额（栈高、脚本长度、EMBED / GOTO 的次数与深度），并确定了三层成本预算（单输入、单交易、单区块）和成本函数的原则：成本是确定性的，只与指令性质和实参大小有关，与硬件无关。

缺的是：其余的限额项、成本函数的具体形状、各类指令的初始成本，以及预算的数值。

EACH 的迭代次数取决于集合大小，嵌套几层就是指数级；循环中反复拼接字符串，数据量也会快速增长。固定长度的脚本必然终止，但开销只能由成本预算约束。


## 决策

### 1. 硬限额（共识规则，超出即失败）

| 项目 | 上限 | 来源 |
| --- | --- | --- |
| 数据栈高度 | < 256 | 构想层 |
| 实参区条目 | ≤ 1024 | 作者提议，与集合成员数一致 |
| 局部域 | 128 项 / 块 | 构想层 |
| 全局变量 | 256 槽 / 脚本域 | 构想层 |
| 普通数据项 | ≤ 8KB | Q15 |
| Script 值与源码类取值 | ≤ 16KB | Q8 |
| 集合成员数 | ≤ 1024 | 切片、字典均适用 |
| 块嵌套深度 | ≤ 16 | 作者提议；每段字节码分别计算，加载期判定 |
| EVAL 嵌套 | 禁止 | 构想层 |
| EMBED | ≤ 4 次，深度为 0 | 构想层 |
| GOTO | 每个脚本 ≤ 2 次，深度 ≤ 3 | 构想层 |
| 外部脚本加载总数 | ≤ 8 次 / 输入 | `GOTO`、`EMBED`、`SCRIPT` 合计，包括子脚本和 EVAL 代码（其中只可能有 `SCRIPT`）中的加载 |
| 解锁脚本、锁定脚本 | 各 ≤ 8KB | 构想层 |
| 表达式 `()` | ≤ 255 字节 | 构想层（1 字节附参） |
| 正则字面量 | ≤ 255 字节 | 构想层 |
| BigInt | 绝对值 ≤ 1016 位 | 构想层、DEC-0005 |
| OUTPUT 缓存 | 无共识限额 | 公共节点上是空操作，私有节点自行限制 |

说明：

- **普通数据项**指标量值：String、Bytes、BigInt、RegExp 等。8KB 能放下 SLH-DSA-128s 的单个签名（7856 字节）和 ML-DSA-87 的签名（4627 字节）。
- **源码类取值**指 `SOURCE`、`IN{Locked}`、`IN{Unlock}`、`IN{Source}`、`OUT{n, Locked}`、`INOUT{n, Locked}`、`XFROM{Locked}`、`XFROM{Source}` 的结果，以及 `CODE`、`SCRIPT` 创建的 Script 值。`SOURCE[0x80]` 返回解锁加锁定的完整字节码，最长约 16KB。
- **切片和字典作为整体不受单项大小上限约束**，由成员数上限、每个成员各自的上限，以及按字节计的分配成本共同约束。例如多签时的签名集是切片，3 个 ML-DSA-65 签名（每个 3309 字节）合计约 9.9KB。签名通过系统占位符从见证信息取得，不计入解锁脚本的 8KB（构想层「解锁脚本长度」的注）。
- **外部加载总数**：按构想层的次数与深度，单个输入最多可以加载 74 次（深度 3、每层 2 次 GOTO 共 14 个子脚本，每个脚本再 EMBED 4 次），所以另设总数上限。
- **嵌套深度按段计算**：解锁脚本、锁定脚本、每个 GOTO / EMBED 目标、每段 EVAL 代码各自不超过 16 层。实际的递归深度因此有界（GOTO 深度 ≤ 3，EVAL 不可嵌套）。

### 2. 成本函数的原则

构想层的原则不变：成本是指令性质与实参大小的确定性函数，与硬件无关。在此之上补三条：

1. **每条被执行的指令至少计 1 个单位**（基础分派成本），包括公共节点上作为空操作的 `PRINT`、`FN_PRINTF`、`OUTPUT`、`BUFDUMP`。否则零成本的指令放进循环里可以被无限放大。
2. **新分配的数据按字节计成本**：每产生 64 字节新数据计 1 个单位。这样单个输入的成本预算同时也限制了内存总量（单输入硬上限 100 万单位时，累计分配不超过约 64MB），不需要单独做内存计量。
3. **跳过的代码不计执行成本**，但每个被加载的段，在加载期按其总长度计费。

公式的形状是：`成本 = 1 + 按字节项 + 按成员项 + 特殊项`。

### 3. 初始成本表

数值都是校准的起点，用基准测试校准之后再冻结（第 5 条）。

| 类别 | 成本 |
| --- | --- |
| 值、截取、栈操作、比较、逻辑、环境取值（`ENV`、`IN`、`OUT` 等）、系统占位符 | 1 + 涉及条目数 + ⌈新数据字节 / 64⌉ |
| 集合操作（`MERGE`、`REVERSE`、`SPREAD`、`ANYS`、`EVERY` 等） | 1 + 成员数 + ⌈新数据字节 / 64⌉ |
| Int 运算 | 2 |
| BigInt 运算 | 加减与位运算：2 + w；乘、除：2 + w²（w 为操作数的 64 位字数，最多 16） |
| 字符串、字节的拼接与转换 | 1 + ⌈结果字节 / 64⌉ |
| 哈希 | 20 + ⌈输入字节 / 64⌉ × k（k 按算法校准，BLAKE3 约 1，SHA3 约 3） |
| `FN_BASE58` | 编码时实参（Bytes）≤ 256 字节，解码时结果（Bytes）≤ 256 字节，超出即失败；成本按输入长度的平方计（Base58 编解码的耗时与长度平方成正比），系数待校准 |
| 签名验证 | 按宿主规格中的算法分别定价，量级约 1000 |
| `FN_PUBHASH`、`FN_MPUBHASH`、`FN_ADDRESS` | 由宿主规格给出（DEC-0002） |
| 正则 | 编译（加载期）：10 + 模式字节；匹配：⌈输入字节 × 模式字节 / 8⌉ |
| `MODEL` | 10 + 每次指令比较 1；`...` 的每一次尝试都计入 |
| `EACH` | 每轮 1 |
| `MAP` / `FILTER` | 建域 5，每轮 2 |
| `EVAL` | 10 + ⌈代码字节 / 64⌉ |
| 外部加载（`GOTO`、`EMBED`、`SCRIPT`） | 200 + ⌈脚本字节 / 64⌉ |
| 加载期结构扫描 | 每段 ⌈字节数 / 64⌉ |

- **外部加载按固定成本计**，不论默克尔证明是用户携带的，还是节点自己查到的（P1-6）。这样带不带证明不影响成本，只影响验证速度。构想层「带证明的交易更快被收录」的激励不变，节点验证证明的开销也有了对应的成本。
- 正则匹配的成本按 Go RE2 引擎最坏情况与「输入 × 模式」成正比估算。

### 4. 预算

按作者提议（2026-11-01），单输入、单交易的基础预算取初稿的 5 倍，区块预算取初稿的 8 倍；按作者增补提议（2026-11-18），单输入、单交易另设硬上限，为基础预算的 2 倍：

| 预算 | 核心默认值 | 配置层级 | 含义 |
| --- | --- | --- | --- |
| `MaxInputScriptCost` | 500,000 | 核心级：核心给出默认值，宿主规格可以改写 | 单输入的基础预算，宿主据此判定（第 4.1 条） |
| `MaxTxScriptCost` | 5,000,000 | 核心级：同上 | 单交易的基础预算，宿主据此判定 |
| `HardInputScriptCost` | 1,000,000 | 核心级：同上 | 单输入的硬上限，不随增量额度提高 |
| `HardTxScriptCost` | 10,000,000 | 核心级：同上 | 单交易的硬上限，不随增量额度提高 |
| `MaxBlockScriptCost` | 无 | 宿主级：只由宿主规格给出；Evidcoin 初值 4,000,000,000 | 宿主累计 |

- 各层预算都是共识规则。交易的成本是其中所有输入实际执行成本之和，加上创建输出时检查的加载期成本（宿主把这一检查定为共识时，DEC-0004 第 5 条）。区块的成本是其中各交易成本之和。
- 「可配置」指数值由宿主规格确定，不是由节点运营者各自设置。同一宿主的全部节点必须使用相同的值。宿主改写时，硬上限不得低于对应的基础预算。
- **校准方法**：在参考硬件上跑基准，定出 1 个单位约等于多少纳秒，目标约为 100 纳秒。按此估算，单输入、单交易的基础预算约为 50 毫秒、500 毫秒，硬上限约为 100 毫秒、1 秒（单核）。
- **Evidcoin 的区块预算**：40 亿单位约为单核 400 秒，超过 6 分钟的出块间隔，因此依赖两点：不同输入之间可以并行验证（8 核约 50 秒）；Evidcoin 采用组队校验，每个节点只验证区块中的一部分交易（作者说明）。宿主规格需要写明这一前提。
- 对照：一次标准单签 `SYS_CHKPASS` 约 1,000–2,000 单位；三层嵌套的 `EACH` 各遍历 255 项需要 1,600 万单位以上，仍会被单输入硬上限直接拦下。

#### 4.1 增量额度（作者增补提议，2026-11-18）

交易可以带有一份**增量额度** Q（成本单位）。Q 如何取得由宿主规格规定，不提供时 Q = 0。Evidcoin 用交易费购买：以前期平均交易费的 2% 为一个单位，每单位 1 万（10,000）额度。

- **只有超出基础预算的部分消耗增量额度**，单输入与单交易两层合并计算，同一单位成本只计一次。设 cᵢ 为各输入的实际成本，C 为交易的成本：

  ```
  E_in = Σ max(0, cᵢ − MaxInputScriptCost)
  E_tx = max(0, C − MaxTxScriptCost)
  消耗 U = max(E_in, E_tx)
  ```

  即：各输入超出单输入基础预算的部分全部消耗增量额度；此外，交易的成本中未被计为输入超出的部分（各输入在基础预算以内的成本，加上创建时检查的成本），合计超出单交易基础预算的部分，也消耗增量额度。
- **输入之间不调配富余**：某个输入未用完的基础预算，不抵充其它输入的超出。
- **硬上限不可突破**：cᵢ ≤ `HardInputScriptCost`，C ≤ `HardTxScriptCost`，与 Q 的大小无关。
- **交易的判定**：每个输入都通过，C ≤ `HardTxScriptCost`，且 U ≤ Q，否则交易无效。Q = 0 时即原来的两条预算（cᵢ ≤ `MaxInputScriptCost`，C ≤ `MaxTxScriptCost`）。
- **单输入的执行预算**：核心 VM 对每个输入使用 min(`HardInputScriptCost`, `MaxInputScriptCost` + Q)，超出即该输入失败。交易级的判定由宿主在全部输入验证之后进行。这样结论与输入的验证顺序无关，输入之间仍可并行验证；代价是一个输入可能执行通过，交易却因各输入合计消耗超过 Q 而无效。
- 区块预算不变：区块的成本包括各交易消耗增量额度的部分。

### 5. 冻结

- 校准完成后，成本表与硬限额随脚本版本冻结（DEC-0004）。此后调整只能通过新版本。
- 各项预算、硬上限与增量额度的取得规则不随脚本版本变化，它们是宿主的共识参数。上线后调低预算或硬上限是规则收缩（强分叉），调高是规则扩展（弱分叉），由宿主按其升级机制处理（`Design.md`「附：分叉种类」）。

### 6. 交易费与成本

构想层原定不在协议层把交易费与成本挂钩。作者 2026-11-18 改为适度挂钩：交易可以用交易费购买增量额度（第 4.1 条），属于宿主的共识规则。除此之外，交易费与成本的关系仍由铸造者自行选择，节点的转发策略中建议：

- 按「(手续费×币权) ÷ max(交易字节数, 成本折算的字节数)」排序转发和打包，类似 Bitcoin 把签名操作数折算进虚拟大小；
- 对频繁转发验证失败交易的对等节点降低信任。

> **概念：**
> 币权 = 币量 × 币龄。
> 币量单位 `chx`，`1 chx = 100 sat`；币龄单位：小时。


## 理由

- **硬限额与成本预算分工**：硬限额约束单个结构的大小（栈、集合、嵌套、加载次数），便于实现预分配和防止递归过深；成本预算约束总的计算量与内存量。只靠成本预算，单个操作仍可能一次性申请巨大的内存；只靠硬限额，循环组合仍能放大开销。
- **按字节计分配成本**，用一个预算同时约束时间和内存，不需要第二套计量。
- **每条指令至少 1 个单位**，堵住「零成本指令 × 循环」的放大。
- **嵌套取 16**：常见脚本的嵌套很少超过 6 层（例如 `EACH{ IF{ SWITCH{ CASE{ … } } } }` 是 4 层），16 层留有充分余量，同时限制解释器的递归深度。
- **实参区取 1024**：数据栈放不下时可以借实参区周转（作者提议）；与集合成员数一致，`@SPREAD` 一个满员集合正好放得下。
- **交易费购买增量额度**（作者增补提议）：固定的预算对确有需求的业务过于死板，用户提高交易费即可完成。额度按前期平均交易费的比例定价，随网络的费用水平自动调节；硬上限保证最坏情形仍然有界。
- **两层合并、不重复计**：一个输入的超出同时也抬高交易的成本，若两层分别计费，同一单位成本会被收两次。取 `max(E_in, E_tx)` 等于「输入的超出 + 其余部分对交易基础预算的超出」，每一单位成本至多消耗一次增量额度。
- **执行预算取上界、交易级事后判定**：若按输入的验证顺序依次扣减额度，结论就依赖顺序，也不能并行验证。


## 影响

- Spec 中每条指令的条目增加「成本」一行，写明公式。
- Plan 需要一套基准测试，用于校准成本系数与单位耗时，并记录参考硬件。
- Evidcoin 宿主规格需要给出：签名算法的成本，公钥哈希与地址函数的成本，`MaxBlockScriptCost` 及其依赖的组队校验前提，描述 / 内容长度（构想层 < 2KB）等宿主参数；以及增量额度的购买规则，包括「前期平均交易费」的定义。
- 核心 VM 的单输入执行预算由宿主按第 4.1 条计算后传入；交易级的判定（增量额度的消耗、单交易硬上限）由宿主执行。

## 开放问题

1. 全部成本系数与单位耗时，待基准测试校准。
2. 参考硬件的选择。
3. Evidcoin 各签名算法（单签、多签）的具体成本。
4. Evidcoin「前期平均交易费」的定义（统计窗口、计算方式），以及它为 0 时增量额度如何计算。
5. 以下是对作者增补提议的理解，请作者确认：
   - 「合并计算消耗」按第 4.1 条的 `max(E_in, E_tx)`，同一单位成本只消耗一次；
   - 购买额度的是交易的全部交易费（不是超出最低交易费的部分），单位数向下取整；
   - 单输入的执行预算为 min(`HardInputScriptCost`, `MaxInputScriptCost` + Q)，交易级的判定在全部输入验证之后进行。

> **作者回答：**
> - 3: Evidcoin 链的安全性基于双路哈希耦合，签名仅用于即时安全验证，因此考虑采用抗量子签名算法 ``ML-DSA-65``。
> - 4: Evidcoin 按 6000 个区块为周期，统计计算平均交易费。
> - 5: 购买额度用的是「交易费超出平均交易费」的部分。最低交易费对应系统默认预算额度，其到平均交易费的差额是用户的主动性空间（收录排序）。
>
> 上面 Evidcoin 的部分属于宿主自己的事务，如你所言，核心 VM 接收一个增量额度 Q 即可。
> 宿主会在接收到交易后查看交易费情况，计算出一个增量额度。
