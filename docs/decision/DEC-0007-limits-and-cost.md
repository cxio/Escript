# DEC-0007 资源限额与成本模型

- 状态：待 Reviewer 对作者提议评审后确认
- 日期：2026-10-28
- 覆盖评审条目：P0-7（Q8、Q15，以及作者在 P0-7 中的三项提议）


## 背景

区块链是开放系统，攻击者可以构造极其消耗资源的交易。构想层已经有一组硬限额（栈高、脚本长度、EMBED / GOTO 的次数与深度），并确定了三层成本预算（单输入、单交易、单区块）和成本函数的原则：成本是确定性的，只与指令性质和实参大小有关，与硬件无关。

缺的是：其余的限额项、成本函数的具体形状、各类指令的初始成本，以及预算的数值。

EACH 的迭代次数取决于集合大小，嵌套几层就是指数级；循环中反复拼接字符串，数据量也会快速增长。固定长度的脚本必然终止，但开销只能由成本预算约束。


## 决策

### 1. 硬限额（共识规则，超出即失败）

| 项目 | 上限 | 来源 |
| --- | --- | --- |
| 数据栈高度 | < 256 | 构想层 |
| 实参区条目 | ≤ 1024 | 作者提议，与集合成员数一致 |
| 局部域 | 128 项 / 块 | 构想层 |
| 全局变量 | 256 槽 / 脚本域 | 构想层 |
| 普通数据项 | < 8KB | Q15 |
| Script 值与源码类取值 | ≤ 16KB | Q8 |
| 集合成员数 | ≤ 1024 | 切片、字典均适用 |
| 块嵌套深度 | ≤ 16 | 作者提议；每段字节码分别计算，加载期判定 |
| EVAL 嵌套 | 禁止 | 构想层 |
| EMBED | ≤ 4 次，深度为 0 | 构想层 |
| GOTO | 每个脚本 ≤ 2 次，深度 ≤ 3 | 构想层 |
| 外部脚本加载总数 | ≤ 8 次 / 输入 | `GOTO`、`EMBED`、`SCRIPT` 合计，包括子脚本和 EVAL 代码（其中只可能有 `SCRIPT`）中的加载 |
| 解锁脚本、锁定脚本 | 各 < 8KB | 构想层 |
| 表达式 `()` | ≤ 255 字节 | 构想层（1 字节附参） |
| 正则字面量 | ≤ 255 字节 | 构想层 |
| BigInt | 绝对值 ≤ 1016 位 | 构想层、DEC-0005 |
| OUTPUT 缓存 | 无共识限额 | 公共节点上是空操作，私有节点自行限制 |

说明：

- **普通数据项**指标量值：String、Bytes、BigInt、RegExp 等。8KB 能放下 SLH-DSA-128s 的单个签名（7856 字节）和 ML-DSA-87 的签名（4627 字节）。
- **源码类取值**指 `SOURCE`、`IN{Locked}`、`IN{Unlock}`、`IN{Source}`、`OUT{n, Locked}`、`INOUT{n, Locked}`、`XFROM{Locked}`、`XFROM{Source}` 的结果，以及 `CODE`、`SCRIPT` 创建的 Script 值。`SOURCE[0x80]` 返回解锁加锁定的完整字节码，最长约 16KB。
- **切片和字典作为整体不受单项大小上限约束**，由成员数上限、每个成员各自的上限，以及按字节计的分配成本共同约束。例如多签时的签名集是切片，3 个 ML-DSA-65 签名（每个 3309 字节）合计约 9.9KB。签名通过系统占位符从见证信息取得，不计入解锁脚本的 8KB（构想层「解锁脚本长度」的注）。
- **外部加载总数**：按构想层的次数与深度，单个输入最多可以加载 74 次（深度 3、每层 2 次 GOTO 共 14 个子脚本，每个脚本再 EMBED 4 次），所以另设总数上限。
- **嵌套深度按段计算**：解锁脚本、锁定脚本、每个 GOTO / EMBED 目标、每段 EVAL 代码各自不超过 16 层。实际的递归深度因此有界（GOTO 深度 ≤ 3，EVAL 不可嵌套）。

### 2. 成本函数的原则

构想层的原则不变：成本是指令性质与实参大小的确定性函数，与硬件无关。在此之上补三条：

1. **每条被执行的指令至少计 1 个单位**（基础分派成本），包括公共节点上作为空操作的 `PRINT`、`FN_PRINTF`、`OUTPUT`、`BUFDUMP`。否则零成本的指令放进循环里可以被无限放大。
2. **新分配的数据按字节计成本**：每产生 64 字节新数据计 1 个单位。这样单个输入的成本预算同时也限制了内存总量（预算 10 万单位时，累计分配不超过约 6.4MB），不需要单独做内存计量。
3. **跳过的代码不计执行成本**，但每个被加载的段，在加载期按其总长度计费。

公式的形状是：`成本 = 1 + 按字节项 + 按成员项 + 特殊项`。

### 3. 初始成本表

数值都是校准的起点，用基准测试校准之后再冻结（第 5 条）。

| 类别 | 成本 |
| --- | --- |
| 值、截取、栈操作、比较、逻辑、环境取值（`ENV`、`IN`、`OUT` 等）、系统占位符 | 1 + 涉及条目数 + ⌈新数据字节 / 64⌉ |
| 集合操作（`MERGE`、`REVERSE`、`SPREAD`、`ANYS`、`EVERY` 等） | 1 + 成员数 + ⌈新数据字节 / 64⌉ |
| Int 运算 | 2 |
| BigInt 运算 | 加减与位运算：2 + w；乘、除：2 + w²（w 为操作数的 64 位字数，最多 16） |
| 字符串、字节的拼接与转换 | 1 + ⌈结果字节 / 64⌉ |
| 哈希 | 20 + ⌈输入字节 / 64⌉ × k（k 按算法校准，BLAKE3 约 1，SHA3 约 3） |
| `FN_BASE58`、`FN_ADDRESS` | 输入 ≤ 256 字节，超出即失败；成本按长度的平方计（Base58 编解码的耗时与长度平方成正比），系数待校准 |
| 签名验证 | 按宿主规格中的算法分别定价，量级约 1000 |
| 正则 | 编译（加载期）：10 + 模式字节；匹配：⌈输入字节 × 模式字节 / 8⌉ |
| `MODEL` | 10 + 每次指令比较 1；`...` 的每一次尝试都计入 |
| `EACH` | 每轮 1 |
| `MAP` / `FILTER` | 建域 5，每轮 2 |
| `EVAL` | 10 + ⌈代码字节 / 64⌉ |
| 外部加载（`GOTO`、`EMBED`、`SCRIPT`） | 200 + ⌈脚本字节 / 64⌉ |
| 加载期结构扫描 | 每段 ⌈字节数 / 64⌉ |

- **外部加载按固定成本计**，不论默克尔证明是用户携带的，还是节点自己查到的（P1-6）。这样带不带证明不影响成本，只影响验证速度。构想层「带证明的交易更快被收录」的激励不变，节点验证证明的开销也有了对应的成本。
- 正则匹配的成本按 Go RE2 引擎最坏情况与「输入 × 模式」成正比估算。

### 4. 预算

| 预算 | 初始值 | 归属 |
| --- | --- | --- |
| `MaxInputScriptCost` | 100,000 | 核心 VM 按此中止执行 |
| `MaxTxScriptCost` | 1,000,000 | 宿主累计 |
| `MaxBlockScriptCost` | 由宿主配置；Evidcoin 初值 500,000,000 | 宿主累计 |

- 三层预算都是共识规则。交易与区块的成本是其中所有输入实际执行成本之和。
- **校准方法**：在参考硬件上跑基准，定出 1 个单位约等于多少纳秒，目标约为 100 纳秒。按此估算，单输入、单交易的预算约为 10 毫秒、100 毫秒（单核）。
- **Evidcoin 的区块预算**：固定 6 分钟出块，每个区块至少容纳 1 万笔交易，所以取通用建议值（5000 万）的 10 倍。5 亿单位约为单核 50 秒；不同输入之间可以并行验证，8 核约 6 秒，远小于出块间隔。
- 对照：一次标准单签 `SYS_CHKPASS` 约 1,000–2,000 单位；三层嵌套的 `EACH` 各遍历 255 项需要 1,600 万单位以上，会被单输入预算直接拦下。

> **作者提议：**
> - `MaxInputScriptCost` 和 `MaxTxScriptCost` 提升 5 倍，可核心级配置。
> - `MaxBlockScriptCost` 再提升 8 倍（即 40 亿），宿主级配置。
>
> Evidcoin 采用组队校验，每节点验证的交易量可比较少（以支持更大的负载）。

### 5. 冻结

校准完成后，成本表与限额随脚本版本冻结（DEC-0004）。此后调整只能通过新版本。

### 6. 手续费（非共识）

构想层已定：不在协议层把手续费与成本挂钩，由铸造者自行选择。节点的转发策略中建议（作者已同意）：

- 按「手续费 ÷ max(交易字节数, 成本折算的字节数)」排序转发和打包，类似 Bitcoin 把签名操作数折算进虚拟大小；
- 对频繁转发验证失败交易的对等节点降低信任。


## 理由

- **硬限额与成本预算分工**：硬限额约束单个结构的大小（栈、集合、嵌套、加载次数），便于实现预分配和防止递归过深；成本预算约束总的计算量与内存量。只靠成本预算，单个操作仍可能一次性申请巨大的内存；只靠硬限额，循环组合仍能放大开销。
- **按字节计分配成本**，用一个预算同时约束时间和内存，不需要第二套计量。
- **每条指令至少 1 个单位**，堵住「零成本指令 × 循环」的放大。
- **嵌套取 16**：常见脚本的嵌套很少超过 6 层（例如 `EACH{ IF{ SWITCH{ CASE{ … } } } }` 是 4 层），16 层留有充分余量，同时限制解释器的递归深度。
- **实参区取 1024**：数据栈放不下时可以借实参区周转（作者提议）；与集合成员数一致，`@SPREAD` 一个满员集合正好放得下。


## 影响

- Spec 中每条指令的条目增加「成本」一行，写明公式。
- Plan 需要一套基准测试，用于校准成本系数与单位耗时，并记录参考硬件。
- Evidcoin 宿主规格需要给出：签名算法的成本、`MaxBlockScriptCost`、描述 / 内容长度（构想层 < 2KB）等宿主参数。
