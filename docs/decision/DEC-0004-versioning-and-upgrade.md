# DEC-0004 脚本版本与升级

- 状态：Proposed（2026-11-04 按作者的设计调整重写，待作者审定）
- 日期：2026-10-28
- 修订：2026-11-01（`CALL` 方法集与静态方法集分开限定；`EXT_MO` 改为双附参；补加载顺序）；2026-11-04（作者取消宽松通过：未分配码位与未知版本一律失败，升级只通过新版本；分叉改按弱分叉、强分叉、异分叉表述）
- 覆盖评审条目：P1-7（Q6）


## 背景

指令集预留了大量码位（未用区间、量子安全保留区 156–163、`FN_X` / `FN_XX` / `EXT_MO` 的索引空间），模块方法也会随版本增加。需要确定：版本号放在哪里，一个版本冻结哪些内容，遇到未分配的码位或不认识的版本怎么办，以及升级如何进行。

上一稿沿用 Bitcoin 的 OP_SUCCESS 思路：锁定方的脚本遇到未分配码位即「宽松通过」，使新功能可以在原版本内加入。作者在提交 494b9f9 中调整了设计（`Design.md`「未知码位处理」）：

- Evidcoin 的脚本可以是合约，需要完整执行，不宜「看不懂就放行」。
- Evidcoin 采用历史证明（PoH）共识。旧版本的铸造者无法收录新版交易，其分叉的币权销毁量更低，很快会被淘汰，因此铸造者会尽快跟上新版本，不需要靠宽松通过让旧节点继续跟随主链。
- 未知码位与未知版本：无法识别就无法验证，因此失败。

Evidcoin 按规则的变化方向把分叉分为三种（`Design.md`「附：分叉种类」）：**弱分叉**（规则扩展，向后兼容）、**强分叉**（规则收缩，向前兼容）、**异分叉**（规则改变，不兼容）。本决策使用这三个词。


## 决策

### 1. 版本号

- 每个锁定脚本有一个版本号，由创建输出的人决定，花费者不能选择。
- 版本号放在宿主的输出结构里，不放进脚本字节码。具体位置由宿主规格定义（Evidcoin：输出项的版本字节，脚本版本即输出项版本，见 `Design.md`「附：版本关系」）。
- 解锁脚本按它所对应的锁定脚本的版本执行。
- `GOTO`、`EMBED` 引入的脚本，按它们自己所在输出的版本执行。`EMBED` 的代码虽然在当前脚本域内执行，但其中每条指令都按嵌入段自身的版本解码和执行。
- Script 值携带版本：`CODE` 创建的 Script 取其所在段的版本；`SCRIPT` 创建的 Script 取被引用输出的版本。`EVAL` 按 Script 值的版本执行。
- **EVAL 代码的版本不得高于发起 EVAL 的段的版本，否则失败。**
- 节点必须实现全部已发布的版本：已上链的输出永远按其版本的规则验证。

### 2. 一个版本冻结哪些内容

每个版本对应一组表：

- 指令码表，包括每个指令的附参格式与取值范围；取值由表给出的附参（环境字段、方法索引等）同时给出其取值表；
- 环境字段表：`GVAL`、`ENV`、`IN`、`OUT`、`INOUT`、`XFROM`；
- 见证条目表（系统占位符的附参）；
- `FN_X`、`FN_XX`、`EXT_MO` 的索引表，以及哈希算法标识、MODEL 类型标识等其它取值表；
- 各模块和对象的**静态方法表**：方法索引、索引别名、参数类型、返回类型、成本函数、公 / 私域标注；
- 各模块和对象的 **`CALL` 方法集**：可经 `CALL` 按名调用的方法名，及其参数类型、返回类型、成本函数、公 / 私域标注；
- 成本表与硬限额（DEC-0007）。

**一个版本发布之后，它的全部表都不再变化**：既不修改已分配的条目，也不在该版本内分配新的条目。任何增加或修改都通过发布新版本进行（第 4 条）。

### 3. 未分配码位与未知版本：失败

「未分配」包括：当前版本没有分配的指令码（含量子安全保留区 156–163 与构想层标为「未用」的码值），以及附参中当前版本的表里没有的取值：环境字段的索引、见证条目的索引、`FN_X` / `FN_XX` 的索引、`EXT_MO` 的模块索引与方法索引、模块的静态方法索引（如 `MO_MATH{Abs}`）、哈希算法标识、MODEL 的类型标识等。

| 情形 | 处理 |
| --- | --- |
| 任何一段（解锁脚本、锁定脚本、`GOTO` / `EMBED` 的目标、`EVAL` 的代码，包括其中 MODEL 的模式体）含有未分配的码值或附参取值 | 该段加载失败，验证失败（DEC-0003） |
| 锁定脚本、`GOTO` / `EMBED` 目标、`EVAL` 代码的版本是本节点不认识的版本 | 失败 |
| `CALL` 调用的方法不在 `CALL` 指令所在段的版本的 `CALL` 方法集中 | 执行到时失败 |

补充规则：

- 未分配在加载期发现，与是否执行到无关：不会执行到的分支里有未分配码位，同样失败（与结构错误相同，DEC-0003）。
- 码值 `255` 永久保留，任何位置都失败。码值 `254`（系统占位符）已分配，出现在解锁段以外（MODEL 模式体除外）即失败。
- **`CALL` 与静态方法都严格。** 二者的区别只在发现的时点：静态方法以附参索引调用，加载期可见；`CALL` 的方法名是运行时字符串，执行到时才能判定。
- 私有专属指令（浮点字面量、`SYS_TIME`、`SHELL`、`FN_PRIV` / `EXT_PRIV`）属于已分配码位，按构想层规则：公共验证执行到即失败。
- 宿主没有实现的宿主指令，对该宿主而言是未分配码位（DEC-0002）。

### 4. 升级

- **升级的唯一途径是发布新版本。** 新版本有自己的一组表：可以增加指令码、取值、方法（包括 `CALL` 方法集）、模块与值类型，也可以调整成本表与硬限额，或在新版本中改变某个条目的语义。
- 旧版本保持原样，旧版本的输出继续按旧规则验证。所以就脚本规则而言，发布新版本是**弱分叉**：新节点接受旧节点接受的全部交易，此外还接受新版本的交易。
- 没有升级的节点遇到新版本的输出即失败（第 3 条）。在 Evidcoin 中，旧版区块不能收录新版交易，新旧两条分叉由分叉竞争决出（`Design.md`）。新版本从何时起被接受，由宿主规格规定。
- 新版本改变已有码位的语义时，反编译器与 MODEL 都必须按版本区分。因此码位的语义应尽量在各版本间保持稳定，优先分配新码位。
- **新版本增加值类型时，旧版本的指令遇到该类型的值即失败。** 不同版本的代码可能交换值：`EMBED` 的代码与调用者共享数据栈，`GOTO` 把实参交给目标。这条规则保证旧版本的语义对新类型也有定义。
- **已发布版本的规则不得修改。** 确实需要修改时（例如发现安全缺陷，必须禁用某条指令），属于强分叉或异分叉，不在本决策的升级路径之内，由宿主决定并单独发布。
- 宿主参数（三层预算等）不随脚本版本变化：调低是强分叉，调高是弱分叉（DEC-0007）。

### 5. 转发策略（非共识）

节点不转发、不打包这样的交易：它**创建**的输出使用了本节点不认识的版本，或其锁定脚本按该版本不能成功加载（含未分配码位或结构错误）。这样的输出按当前规则永远无法花费，多半是误操作。


## 理由

- **失败而不是宽松通过**（作者调整）：脚本可以是合约，需要完整执行；在 PoH 共识下，旧节点会自然淘汰，不需要宽松通过来维持跟随。规则因此更简单：一个码位要么按版本的表执行，要么失败，不存在「判通过但不执行」的第三种结论。
- **版本号由锁定方决定**：版本决定锁定脚本的语义，如果花费者可以选择版本，就等于花费者可以选择规则。
- **一个版本发布后不再变化**：每个版本的语义是一个固定的对象，审计、测试向量与其它语言的实现都有确定的依据。上一稿中「条目的生效范围」「版本内激活」等机制随之取消。
- **EVAL 版本不得高于调用段**：取消宽松通过之后，这条规则不再是防止绕过的必要条件（未知版本本来就失败）。保留它，是为了让一个版本的段在验证时只执行该版本已定义的语义：花费者不能借 `SCRIPT` 把更高版本的代码和值引入旧版本的段。这条规则属于各版本自己的规则，新版本可以为它自己的段放宽。`GOTO`、`EMBED` 的目标写在锁定脚本的附参里，由锁定方在创建输出时选定，目标当时已经上链，版本是确定的，所以不受此限制。
- **`CALL` 与静态方法都严格**：上一稿让静态方法宽松，是为了在原版本内以软分叉加入新方法。版本内不再增加条目，这一区别也就不需要了。静态方法索引仍有价值：加载期可见，编码紧凑。
- **新类型对旧指令失败**：如果不规定，旧版本的指令遇到新类型的值时没有定义的行为，不同实现可能给出不同结果。

**不做：** 不在脚本字节码里放版本前缀。版本放在字节码里，就需要处理「解锁脚本自带版本」的情形，而解锁脚本是花费者写的。

**不做：** 不保留任何形式的宽松通过（作者调整）。其它宿主如果需要「不升级全部验证节点就能引入新的脚本功能」，核心不提供这种机制。


## 影响

- Spec 的指令格式表仍标注哪些附参的取值由版本的表给出（字段表、方法表等），但这类附参的未分配取值与其它附参的越界取值处理相同：失败（DEC-0003）。
- 方法表分为两张：静态方法表、`CALL` 方法集，按版本发布，并标注公 / 私域（DEC-0001）。v1 的方法表由评审者在 Spec 中起草，作者审定。
- Script 值在内部需要携带版本号。
- 实现必须同时支持全部已发布的版本，版本表应当是数据驱动的。
- 测试向量需要覆盖：各种段中出现未分配码位（包括不会执行到的分支与模式体内）、未分配的静态方法索引、`CALL` 未知方法、锁定脚本 / `GOTO` / `EMBED` 目标 / EVAL 代码的版本未知、EVAL 代码版本高于调用段。
- 宿主规格需要给出：版本字段及其与核心版本号的对应；新版本从何时起被接受。

## 开放问题

1. **创建输出时是否在共识层校验锁定脚本**（宿主，Evidcoin）。目前只有第 5 条的转发策略。取消宽松通过之后，这一校验变得可行：一个版本的锁定脚本只能使用该版本的码位。好处是链上不会出现因编码错误而永远无法花费的输出，节点也可以缓存解码结果；代价是每个输出在创建时多做一次加载扫描（是否计入交易成本由宿主规定）。

已关闭：Evidcoin 的脚本版本取输出项的版本字节（首字节），一个输出版本对应一个脚本版本。配置字节的高 4 位已经是状态位，不能用于版本。作者在第三轮同意，并说明输出项版本号由用户自己设定、协议不强制其合法性，所以 `SCRIPT` 能引入任意版本号；未知版本在 EVAL 时失败（第 3 条）。写入 Evidcoin 宿主规格。

已关闭（2026-11-04）：软分叉的激活机制。版本内不再增加条目，核心不需要激活机制；新版本从何时起被接受由宿主规格规定（第 4 条）。
