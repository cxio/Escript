# DEC-0004 脚本版本与升级

- 状态：Accepted
- 日期：2026-10-28
- 修订：2026-11-01（采纳作者提议：`CALL` 方法集与静态方法集分开限定；`EXT_MO` 改为双附参；补加载顺序）
- 覆盖评审条目：P1-7（Q6）


## 背景

指令集预留了大量码位（未用区间、量子安全保留区 156–163、`FN_X` / `FN_XX` / `EXT_MO` 的索引空间），模块方法也可以按版本增加。构想层 `Design.md`「未知码位处理」已经确定沿用 Bitcoin 的 OP_SUCCESS 思路：遇到未分配的码位，宽松通过，使将来的新功能可以通过软分叉加入，并且这条规则只适用于锁定方的脚本。

还没有定的是：版本号放在哪里，一个版本冻结哪些内容，宽松通过的确切范围，以及如何保证每一次升级都确实是软分叉。


## 决策

### 1. 版本号

- 每个锁定脚本有一个版本号，由创建输出的人决定，花费者不能选择。
- 版本号放在宿主的输出结构里，不放进脚本字节码。具体位置由宿主规格定义（Evidcoin：输出项的版本字节）。
- 解锁脚本按它所对应的锁定脚本的版本执行。
- `GOTO`、`EMBED` 引入的脚本，按它们自己所在输出的版本执行。`EMBED` 的代码虽然在当前脚本域内执行，但其中每条指令都按嵌入段自身的版本解码。
- Script 值携带版本：`CODE` 创建的 Script 取其所在段的版本；`SCRIPT` 创建的 Script 取被引用输出的版本。`EVAL` 按 Script 值的版本执行。
- **EVAL 代码的版本不得高于发起 EVAL 的段的版本，否则失败。**

### 2. 一个版本冻结哪些内容

每个版本对应一组表：

- 指令码表，包括每个指令的附参格式、取值范围，以及哪些附参属于索引类；
- 环境字段表：`GVAL`、`ENV`、`IN`、`OUT`、`INOUT`、`XFROM`；
- 见证条目表（系统占位符的附参）；
- `FN_X`、`FN_XX`、`EXT_MO` 的索引表，以及哈希算法标识等其它索引类附参的取值表；
- 各模块和对象的**静态方法表**：方法索引、索引别名、参数类型、返回类型、成本函数、公 / 私域标注；
- 各模块和对象的 **`CALL` 方法集**：可经 `CALL` 按名调用的方法名，及其参数类型、返回类型、成本函数、公 / 私域标注；
- 成本表与硬限额（DEC-0007）。

**已分配的条目永不修改。** 未分配的条目可以在将来分配，规则见第 4 条。`CALL` 方法集例外：一个版本发布后，其中任何模块或对象的 `CALL` 方法集都不再增减（第 3、4 条）。

### 3. 未分配码位：宽松通过

「未分配」包括：当前版本未分配的指令码（含量子安全保留区 156–163），以及索引类附参中未分配的取值。索引类附参包括：环境字段的索引、`FN_X` / `FN_XX` 的索引、`EXT_MO` 的模块索引与方法索引、模块的静态方法索引（如 `MO_MATH{Abs}`）、哈希算法标识、MODEL 的类型标识等。Spec 在指令格式表中逐条标注。非索引类附参取值越界属于结构错误（DEC-0003）。

| 出现在哪里 | 处理 |
| --- | --- |
| 锁定脚本、`GOTO` / `EMBED` 的目标脚本（锁定方的脚本） | 该段加载时，**整个输入的验证立即判为通过**，不再执行任何指令 |
| 解锁脚本 | 失败 |
| `EVAL` 执行的代码 | 失败 |

补充规则：

- 宽松通过的范围是整个验证，而不只是那一段脚本。否则旧节点会让 `GOTO` 目标「通过」后回到调用者继续执行，而新节点执行了新语义，两边的后续结果可能不同。
- 一段之内按字节顺序解码，先遇到的结构错误或未分配码位决定该段的加载结果；各段的加载顺序见 DEC-0003 第 1 条。
- 码值 `255` 永久保留，任何位置都失败。码值 `254`（系统占位符）已分配，出现在解锁段以外即失败。
- **`CALL` 严格，静态方法宽松**（作者提议）。`CALL` 的方法名是运行时字符串，加载期看不到，不适用宽松通过：调用当前版本 `CALL` 方法集中没有的方法即失败。模块与系统对象（`Time` 对应 `MO_TIME`，`RegExp` 对应 `MO_RE`，扩展模块对应 `EXT_MO`）的静态方法以附参索引调用，加载期可见，适用宽松通过。
- 私有专属指令（浮点字面量、`SYS_TIME`、`SHELL`、`FN_PRIV` / `EXT_PRIV`）属于已分配码位，按构想层规则：公共验证执行到即失败。
- 宿主没有实现的宿主指令，对该宿主而言是未分配码位（DEC-0002）。

### 4. 如何保证升级是软分叉

软分叉要求：新规则下有效的，旧规则下也有效。据此：

- **在原版本内给未分配码位赋义**：赋义后，新语义只在锁定方的脚本中生效。在解锁脚本和 EVAL 代码中，该码位在原版本下仍按未分配处理（失败）。旧节点对锁定方脚本判通过，新节点执行新规则，结果只会更严，属于软分叉。如果新语义也在 EVAL 代码中生效，原本失败的 EVAL 代码就可能变成通过，那是放宽规则，属于硬分叉。
- **给已有模块增加方法**：在原版本内只能作为静态方法加入（分配一个静态方法索引），按上一条处理。同一版本内不能把它加入 `CALL` 方法集：旧节点调用未知方法即失败，新节点调用成功，这是放宽规则，任何人构造一笔这样的交易就能造成分叉。新方法要经 `CALL` 调用，只能在新版本中加入该版本的 `CALL` 方法集。
- **新分配的模块**（例如一个新的 `EXT_MO` 模块索引）随分配一起给出它的 `CALL` 方法集，之后冻结。该模块的对象只能由锁定方脚本中的构造指令产生，而旧节点在加载该段时已判通过，所以它的 `CALL` 调用不会引起分歧。
- **需要在解锁脚本或 EVAL 代码中使用新码位**，或需要改变已分配条目的语义时，发布新版本。

由此，一个新方法的典型路径是：先在当前版本中作为静态方法以软分叉加入；下一个版本发布时，再进入 `CALL` 方法集。

### 5. 未知版本

- 锁定脚本、`GOTO` / `EMBED` 目标的版本号是本节点不认识的版本：该段加载时，整个验证判为通过（与未分配码位相同）。
- EVAL 代码的版本高于发起 EVAL 的段的版本（第 1 条）：失败。在新旧节点上都失败，所以不会分叉。

### 6. 转发策略（非共识）

节点不转发、不打包这样的交易：它**创建**的输出的锁定脚本含有未分配码位，或使用了本节点不认识的版本。这样可以防止有人误把资金锁进实际上任何人都可以花费的脚本。


## 理由

- **版本号由锁定方决定**：版本决定锁定脚本的语义，如果花费者可以选择版本，就等于花费者可以选择规则。
- **宽松通过只给锁定方的脚本**：解锁脚本由花费者编写，EVAL 的代码也可能来自花费者（解锁区可以用 `CODE`、`SCRIPT` 创建 Script 值）。在这些地方宽松通过，花费者放一个未分配码位就能直接通过。
- **EVAL 版本不得高于调用段**：解锁区允许 `SCRIPT`，花费者可以引用任何已上链的输出，包括使用了未知版本的输出。如果 EVAL 遇到未知版本也判通过，锁定脚本对 EVAL 结果的检查就被绕过了。规定「不得高于」而不是「判通过」，新旧节点都失败，不会分叉。`GOTO`、`EMBED` 的目标写在锁定方脚本的附参里，花费者无法改变，所以它们可以按未知版本宽松通过。
- **方法名走动态路径就不宽松**：加载期看不到运行时字符串，无法在执行前判定；执行到一半再判通过，会让旧节点和新节点在此之前的执行结果不同。
- **静态方法与 `CALL` 方法集分开**（作者提议）：如果新方法只能经 `CALL` 使用，每次给模块加方法都是硬分叉。静态索引让新方法可以先以软分叉上线，`CALL` 的扩展则留给计划内的版本发布。

**不做：** 不在脚本字节码里放版本前缀。版本放在字节码里，就需要处理「解锁脚本自带版本」的情形，而解锁脚本是花费者写的。

**不做：** 不为 `CALL` 的新方法预设「到某个时间后才开启」的规则（作者提议中的参考做法，作者同意略去）。`CALL` 方法集按版本冻结，已经足以保证软分叉；时间开关会引入「同一版本在不同时刻语义不同」的情形。


## 影响

- Spec 的指令格式表需要标注每个附参是否属于索引类（DEC-0003）。
- 方法表分为两张：静态方法表、`CALL` 方法集，按版本发布，并标注公 / 私域（DEC-0001）。v1 的方法表由评审者在 Spec 中起草，作者审定。
- Script 值在内部需要携带版本号。
- 测试向量需要覆盖：锁定段、`GOTO` / `EMBED` 目标、解锁段、EVAL 代码中分别出现未分配码位的四种情形，未分配的静态方法索引，`CALL` 未知方法，以及 EVAL 代码版本高于调用段的情形。
- 宿主需要提供软分叉的激活机制（何时开始执行新语义）。
