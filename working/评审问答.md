### 对作者新增设计的意见

- **系统占位符（254）**：接受。第二轮曾建议 254、255 都永久保留，现在 254 用作占位符，只保留 255。原文「执行前替换为值指令」会改变字节码的偏移，与 `SOURCE`、NULL 点、`MODEL` 冲突，按 Q14 改为执行时压入见证条目、不改写字节码。见证条目表属于宿主规格（DEC-0002）。
- **未知码位宽松通过**：接受，但原文缺少「只适用于锁定方」的限制，花费者在解锁脚本里放一个未分配码位（例如 14、15），或一个未分配的 `GVAL` 索引，就能直接通过。已补上这条限制，并把范围从「该脚本通过」改为「整个验证通过」（理由见 DEC-0004 第 3 条）。
- **超级赎回**：不进入本轮 Decision。它让原本无法花费的输出变得可以花费，是放宽规则，属于硬分叉，不能走 DEC-0004 的软分叉路径；语义上属于 Evidcoin 宿主的 `SYS_CHKPASS`。将来采纳时，还需要单独论证特权私钥这个信任点。
- **模块方法的静态索引**（`MO_MATH{Abs}`）：接受。静态索引是索引类附参，未分配的索引在锁定方的脚本中按宽松通过处理；`CALL` 的动态方法名不适用，调用不存在的方法即失败（DEC-0004）。


### 对第二轮回复的两处修正

**P1-7 的版本方案。** 第二轮的方案有两处不一致，DEC-0004 已修正：

1. 「每个版本的表冻结、只增不改」与「在原版本内给未分配码位赋义（软分叉）」并存，但没有说明新赋义在哪里生效。修正为：已分配的条目永不修改；原版本内的新赋义只在锁定方的脚本中生效；解锁脚本和 EVAL 代码要使用新码位，需要发布新版本。
2. 「`SCRIPT` 引入的脚本按其所在输出的版本执行，未知版本判通过」可以被利用：解锁区允许 `SCRIPT`，花费者可以引用一个使用未知版本的输出，交给 EVAL 执行，从而直接通过。修正为：EVAL 代码的版本不得高于发起 EVAL 的段，否则失败。

**P1-1 的表达式类型。** 第二轮回复写的是「表达式的结果有 BigInt 操作数时为 BigInt」。构想层 `9.运算指令.md` 的符号指令只支持 Int | Float，DEC-0005 按构想层执行：表达式内出现 BigInt 操作数即失败，BigInt 运算使用命名指令（`ADD`、`MUL` 等）。

## P0 阻断



### P0-1 默认通关为真，且解锁区允许 INPUT

**问题**

初始通关状态为 true。`INPUT` 在解锁脚本白名单之内。公共节点上 `INPUT` 没有数据就中断退出，且不影响 PASS 状态。解锁脚本先于锁定脚本执行。

**影响**

花费者在解锁脚本里只写一个 `INPUT`，公共节点会在锁定脚本（包括 `SYS_CHKPASS`）执行之前就以“通过”结束。空锁定脚本、条件为假因而没执行到的 `IF{ … PASS }`、对外部提供的 `CODE{INPUT}` 执行 `EVAL`，也会默认通过。

**建议**

初始状态改为「未决」，结束时至少有一次成功的 PASS / CHECK / SYS_CHKPASS 才算通过。`INPUT` / `END` 在公共节点上的含义是「以当前状态结束」，不是「通过」。解锁区至少移除 `INPUT`、`OUTPUT`、`BUFDUMP`、`PRINT`、`CALL`。更彻底的方案见 P0-6。

**依据**

- `docs/conception/Instruction/6.结果指令.md`
- `docs/conception/Instruction/5.交互指令.md`（`INPUT` 中断不影响通关）
- `docs/conception/Design.md` 解锁脚本区段

#### 回答

已在文档中修订。
默认可自由通行：只有设置检查，才需要阻止，符合社会伦理。——这是一个重要原则。

#### 评审回复

接受「默认可自由通行」作为设计原则。Bitcoin 同样允许创建任何人可花费的输出，由锁定方自己负责。修订后 `INPUT` 已不在解锁区，评审时的那条攻击路径已经关闭。

这个原则有一个推论：既然默认通过，安全性就完全取决于「锁定脚本被完整、按原意执行」。凡是能让花费者提前结束锁定脚本、或改变锁定脚本语义的机制，都会直接变成放行漏洞。本轮核对发现两处：

1. 解锁段留在实参区的值，会被锁定脚本的第一条取参指令使用。这是新问题，单列为 [P0-8](#p0-8)。
2. EVAL 内的 `END` / `INPUT` 会向外传递「结束」。`CODE` 在解锁区可用，如果锁定脚本 EVAL 的代码来自花费者，花费者只要在代码里写一个 `END`，锁定脚本在 EVAL 之后的检查就全部跳过。建议见 [P1-3](#p1-3) 与 Q3。

另外需要写明一条解析规则：解锁脚本和锁定脚本分别解析，任何指令（包括 `DATA` 的长度、块长度）都不能跨越两段的边界。否则解锁脚本末尾一个长度声明过大的 `DATA`，就能把锁定脚本开头的若干字节吞成数据。



### P0-2 通关状态是一个可被覆盖的单变量

**问题**

`PASS(true)` 会设置通关状态，`CHECK` 以最后一次为准，`SYS_CHKPASS` 也是通关指令，三者共用一个变量。于是 `CHECK(false) … PASS(true)` 或 `CHECK(false) … SYS_CHKPASS` 最终是通过。GOTO 目标脚本里的 CHECK 也能覆盖调用者之前的失败。

**影响**

「多个 PASS 类似 And」只在没有 CHECK 时成立。审计者难以判断一段脚本最终的通关条件。

**建议**

拆成两个量：PASS 链（任一失败立即终止）与 CHECK 槽（最后一次为准）。最终结果 = PASS 链未失败，且 CHECK 槽未设置或为真，且至少发生过一次检查。并写明 GOTO / EMBED / EVAL / MAP 对这两个量的读写规则。

**依据**

- `docs/conception/Instruction/6.结果指令.md`（PASS、CHECK、GOTO 共享通关状态）
- `docs/conception/Instruction/15.系统指令.md`（`SYS_CHKPASS` 也是通关指令）



#### 回答

PASS 和 CHECK 的通关状态不应分开，它们是不同的现实需求，但应对应到同一结果——是否放行。如何合理组合使用是人的责任。

已在 PASS 指令的说明处提示了 CHECK 的影响。GOTO / EMBED / EVAL 也补充了说明。MAP 只是独立的脚本域，PASS/CHECK 属于系统域，脚本域是系统域的子域，子域隔离并不能影响父级域，所以通关状态依然共享。

#### 评审回复

接受。PASS 与 CHECK 共用一个状态，规则现在是确定的，可以直接写成状态机：

- 初始：未决。
- `PASS(true)`、`CHECK(true)`、`SYS_CHKPASS` 成功：置为「通过」，继续执行。
- `CHECK(false)`：置为「未通过」，继续执行。
- `PASS(false)`、`SYS_CHKPASS` 失败、运行错误：立即结束，结果为失败。
- 正常结束（执行完毕、`EXIT`、公共节点上的 `END` / `INPUT`）：状态为未决或通过则放行，为未通过则失败。

还剩一处需要定：GOTO 目标脚本里的 `PASS(false)`。按 P1-3 的回答，它只「结束该子脚本」，那么调用者会继续执行，之后的 `PASS(true)` 可以把状态改回通过，目标脚本的否决就失效了。GOTO 的典型用途是「管理者 + 审计者 + 第三方」，审计脚本的否决能被调用者覆盖，大概不是你想要的。见 [P1-3](#p1-3) 与 Q2。

另外建议在 EVAL 的说明里加一句：EVAL 有自己独立的通关状态，调用者看不到。调用者如果需要知道 EVAL 的结论，只能通过 EVAL 留在栈上的数据。

> **作者补充：**
> CHECK(false) 仅属于脚本域的临时状态，但 PASS(false) 会即时透传。
> 详细修改已经反应在 [P1-3](#p1-3) 小节和 Conception 中。



### P0-3 实参区的取值规则与示例互相矛盾

**问题**

规则是：实参区有值就从实参区取，条目数必须匹配；无值才从数据栈取。但 `EACH` 示例里 `$Value {10} GT`（循环变量进实参区、`{10}` 入栈，GT 需要 2 个）只有在「实参区不足的部分从栈补齐」时才成立。评审时的两个 CALL 示例，第一次调用的结果留在实参区，第二次调用按哪种模型都拿不到预期参数。

**影响**

实参区是这套设计的核心机制，规则不唯一就无法写 Spec。另外 `@INPUT`、`@SPREAD`、`@POPS[0]`、`@KEYVAL` 以及 MODEL 的双返回值都让实参区条目数到运行时才确定，下一条指令从哪里取参无法静态判断。

**建议**

两种模型二选一并写死：严格匹配，或先实参区、不足部分从栈补齐。对实参区占用做静态检查，无法静态确定时拒绝该脚本。同步修正示例。

**依据**

- `docs/conception/Design.md` 实参空间、指令的参数配置
- `docs/conception/Instruction/7.流程控制.md` 的 BREAK 示例
- `docs/conception/Instruction/14.工具指令.md` 的 CALL 示例

#### 回答

局域存值/取值指令已修订，且字面符号从 `$` 变成了 `&`（与模式指令中的正则匹配取值互换）。局域取值应当自动入栈，截留到实参区依然需要前置 `@` 指令。这是一个文档失误，已修订。

实参区取值规则已经过成熟思考（一次性取完），简化人类认知和记忆负担，也更简洁。

关于实参条目数静态可确定的问题，实际上我觉得没必要这样限制。实参数量应当是自由和灵活的，就像一种语言里函数的参数数量一样——是天然不应该限制的，不然就太死板了，会影响逻辑表达。

CALL 指令的示例已经修订，应当是临时放入局域（`&CALL[...]`），这样才不影响实参区/数据栈的正常运作。属于文档失误。

#### 评审回复

接受。「有值则必须恰好 n 项、一次取完；无值才从栈取」这条规则清楚，运行时数量不符即失败，结果是确定的，不需要静态可判定。

我按这条规则重新推演了修订后的示例：EACH / BREAK、MAP、FILTER、RANGE 合并、CALL（时间对象）、Design.md 的定制验证、README 示例都成立。另有两处与实参区无关的小错，列在[第二轮小结](#round2)的勘误里（SLRAND 的 `{-2} PEEK`，CALL 第二例的浮点注释）。

运行时才知道实参区的占用，本身不是问题。真正的风险出在信任边界上：解锁脚本也能往实参区放值，见 [P0-8](#p0-8)。



### P0-4 浮点数进入了共识路径

**问题**

评审时，表达式 `()` 一律转成 float64 并返回 Float；`POW` 用 `math.Pow`；`MO_MATH` 全部是 float64；`RANGE`、`RANDOM` 支持浮点。

**影响**

int64 超过 2^53 后静默丢精度，金额放进表达式就会算错。Go 在 arm64、ppc64le、s390x 上可能把乘加融合为 FMA，不同架构的节点可能得出不同结果。`RANGE` 的浮点步进是逐次累加还是 `start + i×step` 没有定义。文档示例把表达式结果写成了整数。

**建议**

表达式默认按 Int 计算，溢出即失败，遇到 Float 才提升。共识路径禁止浮点，或严格限定（显式舍入、禁止 FMA、固定实现）。浮点能力只开放在 END 之后的私有段。

**依据**

- `docs/conception/Instruction/9.运算指令.md`
- `docs/conception/Instruction/1.值指令.md` 浮点字面量
- `docs/conception/Instruction/17.模块指令.md` 的 `MO_MATH`
- `docs/conception/Design.md`「私有专属」

#### 回答

已部分接受建议并修订原始设计。

#### 评审回复

方向是对的，还差一点。现在的写法是「浮点字面量（opcode 7）在公共验证中遇到即失败」，但 Float 还有别的来源：

- `FLOAT` 转换（opcode 72）可以把整数或字符串转成浮点数；
- `ANYS[7]` 可以把 `[]any` 转成 `[]Float`；
- 模块方法（如 `MO_MATH`）可能返回浮点数。

只禁字面量，这些路径照样能在公共域里产生浮点数。建议把规则改为：**Float 是私有域类型，公共验证中任何指令产生 Float 值（进入栈、实参区、局域或集合）即失败。** 实现上只需要在构造 Float 值的一处检查，`RANGE`、`RANDOM`、`MO_MATH` 就不必逐个限制。见 Q9。

私有域里浮点可以照常使用。私有域不参与共识，FMA 等跨平台差异只影响本地结果。



### P0-5 语义由 Go 标准库的行为定义，而不是由规格定义

**问题**

正则用 Go regexp（`(?i)`、`\p{…}` 依赖随 Go 版本更新的 Unicode 表）。随机数写的是 `math/rand/v2` 的 ChaCha8，但取整、取浮点和打乱的派生算法不在 ChaCha8 规范之内。CALL 直接暴露 `time.Time` 的 Day / Clock / Format。`MO_FMT` 暴露 `fmt.Sprint`。转换依赖 strconv 与 math/big。数据栈直接定义为 `[]any`。

**影响**

节点升级 Go 版本就可能改变脚本结果。用其他语言实现兼容节点几乎不可能，与「通用化使用」冲突。

**建议**

在 Decision 层明确规格的权威来源：要么规格自足（逐字节定义算法并附测试向量），要么「参考实现即规格」并冻结 Go 版本与依赖。`RANDOM` / `SLRAND` 需要规定从种子到结果的完整算法。

**依据**

- `docs/conception/Design.md` 数据栈 `[]any`
- `docs/conception/Instruction/1.值指令.md` 正则
- `docs/conception/Instruction/14.工具指令.md` 随机数与 CALL
- `docs/conception/Instruction/17.模块指令.md`



#### 回答

这个可以探讨一下，具体怎么实现比较合适？自定规格是否太复杂，初期是否有必要如此。这是一个开放问题。

`RANDOM` / `SLRAND` 的完整算法你可以看着办。

#### 评审回复

结论：初期不需要从零写一份完全自足的规格，但需要明确一条原则：**规格文档加测试向量是权威，Go 实现是参考实现。** 真正需要额外处理的只有下面的第三类行为，而最省事的办法是把它们移出公共域。

脚本的行为可以分成三类：

1. **本设计自己定义的语义**：字节码编码、值类型、栈与实参区、控制流、通关状态、运算规则、MODEL 匹配、限额与成本。这些本来就是 Spec 要写的内容，不依赖外部库，没有额外成本。
2. **已有公开标准的算法**：BLAKE3 / BLAKE2b / SHA2 / SHA3、Base32 / Base64（RFC 4648）、RFC 3339 时间格式、UTF-8、签名算法（如 ML-DSA，FIPS 204）。规格里写明标准名称和版本即可，这些标准都自带测试向量。
3. **由 Go 标准库实现决定、没有独立标准、或会随 Go 版本变化的行为**：
  - 正则的 Unicode 类（`\p{…}`）和 `(?i)` 的大小写折叠依赖 Unicode 表。我在本机核对过：Go 1.27 的 `unicode.Version` 是 17.0.0，而 Go 1.21 是 15.0.0。升级 Go 可能改变匹配结果（主要影响新增字符）。
  - `fmt` 的格式化输出（`MO_FMT`）。格式化字典这类自定义类型时，输出取决于内部数据结构。
  - `time.Time` 的 `Format`，以及依赖本地时区数据库的方法（`Local`、`In`）。时区数据库随操作系统而变。
  - 随机数的派生算法：`IntN`、`Perm` 等不在 ChaCha8 的规范之内。
  - varint：Go 的 `binary.Varint` 接受冗余编码，`[0x80, 0x00]` 也会解出 0（本机已验证），规范编码需要另写规则，见 P0-6。

第三类的处理建议：


| 行为                    | 建议                                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 正则                    | 保留在公共域。规格写明「RE2 语法 + Unicode 版本 X」，CI 断言 `unicode.Version` 等于该值。将来要升级 Go 而 Unicode 版本变化时，把 `regexp` 及其 Unicode 表固化一份到项目内 |
| `MO_FMT`                | 私有域专属。`FN_PRINTF` 已按 P1-8 在公共节点为空操作，不受影响                                                                                 |
| Time 的格式化与时区方法 | 私有域专属。公共域只开放数值读取（年、月、日、时、分、秒、毫秒、Unix 时间戳），时区只认 UTC 和固定偏移                                                                 |
| 随机数                  | 规格自定义完整算法，见下文                                                                                                            |


配套的两项保障：

- **测试向量**：每条指令的正常、边界、失败用例，格式为「字节码 + 环境 → 结果 + 成本」。TDD 本来就要写这些测试，导出成 JSON 就是可供其他语言实现对照的向量集。Bitcoin 的 `script_tests.json`、Ethereum 的 `ethereum/tests` 都是这种做法。
- **固定 Go 工具链**：`go.mod` 固定 toolchain 版本；升级 Go 必须全量通过向量集。

**随机数算法**

建议不再基于 `math/rand/v2`，改用 BLAKE3 的 XOF（可扩展输出）模式。理由：BLAKE3 已经是本系统的默认哈希，不增加依赖；它的密钥恰好是 32 字节，与种子长度一致；各语言都有实现，并有官方测试向量。ChaCha8 虽然有规范，但 Go 之外的实现很少，而且派生方法不在规范之内。

```text
stream(seed, tag)
    BLAKE3 keyed 模式，key = seed（必须恰好 32 字节，否则失败），
    输入 = tag（ASCII 字符串），按 XOF 方式顺序读取任意长度输出。
    tag：RANDOM 用 "escript/RANDOM/v1"，SLRAND 用 "escript/SLRAND/v1"。

next64()
    从流中读取下 8 字节，按大端序解释为 uint64。

uniform(n)，n ≥ 1
    r = (2^64 − n) mod n
    循环：x = next64()，直到 x ≥ r
    返回 x mod n
    （拒绝采样，没有取模偏差；期望读取次数小于 2）

RANDOM(seed, bound Int)
    bound ≥ 1，否则失败；返回 uniform(bound)。

RANDOM(seed, bound Float)        // 私有域
    x = next64() >> 11；返回 x / 2^53 × bound。

SLRAND(seed, s)                  // s 为切片或 Bytes
    t = s 的副本
    i 从 len(t) − 1 递减到 1：j = uniform(i + 1)；交换 t[i] 与 t[j]
    返回 t
    （Fisher–Yates 洗牌）
```

使用提示（建议写进指令说明）：链上的种子是公开的，任何人都能提前算出结果。需要公平性的场景（如抽签），种子应由承诺–揭示（commit–reveal）等方式产生。



### P0-6 缺少规范编码规则，存在延展性风险

**问题**

没有规定唯一编码：varint 是否 zigzag、是否禁止冗余长编码；int64 范围内的值能否用 BigInt 编码、能否有前导零或负零；Float 字节中出现 NaN / Inf / -0 如何处理；字符串是否必须是合法 UTF-8；`_` 与 `_[1]` 是两种等价编码。

**影响**

MODEL 按字节做全等测试，同一个值的不同编码可以绕过模式匹配。解锁脚本若允许计算，第三方可以在不破坏签名的前提下改写它；若解锁脚本计入 TxID，就是交易延展性。

**建议**

为每种值规定唯一的规范编码，非规范即无效。解锁区参考 Bitcoin 的 push-only，只允许值指令（外加 `SYS_NULL`）。明确解锁脚本是否参与 TxID 计算。

**依据**

- `docs/conception/Instruction/1.值指令.md` 整数、大整数、浮点
- `docs/conception/Instruction/12.模式指令.md` 全等测试，以及 `_` 与 `_[1]`
- `docs/conception/Design.md` 解锁脚本区段

#### 回答

- 字符串默认 UTF-8 编码，但 String 类型不检查合法性（如 []byte => string）。
- []rune 必须为合法 Unicode 码点，非法 UTF-8 序列转到 rune 时会替换为 \uFFFD，信息损失。

`_` 和 `_(1)` 已经修改为采用 `.` 和 `.(1)` 字面表示。原 `_` 字符改用于表达新添加的截取指令 `opcode:24` 返回值销毁。但问题依旧：我认为 `.` 和 `.[1]` 虽然效果相同，但编码需要各自表达，因为它们是不同的 opcode。即前者为一字节 `117`，后者为两字节 `118 1`。

varint 的编码按 go 标准库 binary.Varint 的实现规则编码即可。int64 范围内的值用 opcode:5 存储，超出范围的值才需要用 opcode:6 大整数。Float 的值指令不支持 `NaN / Inf / -0` 表达，因此它们只会出现在运行时。`-0` 的处理也遵循 go 语言默认行为即可。

解锁区的指令码允许范围已排除交互指令区，但前面其它几个区的指令还是值得允许的，那样可以让解锁数据的操作更为灵活、精简。

#### 评审回复

`.` 与 `.[1]`：同意，问题撤回。它们是 MODEL 里的模式指令，不是被比较的值，两种写法并存不会带来绕过。

String 不检查 UTF-8 合法性：同意。字符串按字节比较，字节不同就是不同的值，不产生歧义。

需要补的是**规范解码**规则，也就是节点在执行前解析字节码时，哪些编码直接判为无效脚本：

1. varint 必须是最短编码。Go 的 `binary.Varint` 不检查这一点（`[0x80, 0x00]` 也会解出 0），解码后要额外判断：多字节编码的末字节不能是 `0x00`。
2. opcode 6（BigInt）：绝对值必须超出 int64 范围；绝对值不能有前导零字节；不能是「负零」（符号位为 1、绝对值为 0）。
3. opcode 4（Rune）：必须是合法的 Unicode 标量值，即不超过 0x10FFFF，且不在代理区 0xD800–0xDFFF。
4. opcode 7（Float）：字节不能编码 NaN 或 ±Inf。（私有域专用，优先级低）
5. 块长度（`IF{}`、`EACH{}`、`()` 等）必须恰好落在指令边界上，子块必须完整包含在父块内。
6. 解锁脚本与锁定脚本分别解析，指令不能跨越两段的边界（见 P0-1 回复）。

以上都是「解析失败即脚本无效」，与执行路径无关（见 P1-8 回复中的加载期校验）。

**延展性的关键不在编码，而在 TxID 覆盖哪些数据。** 你保留了较丰富的解锁区，这本身没问题，但它意味着第三方可以在不改变语义的前提下改写解锁脚本，例如在末尾追加 `{7} _POP`（压入再丢弃）。如果解锁脚本计入 TxID，而签名又没有覆盖它，第三方就能改掉交易 ID。定制验证中签名本身就放在解锁脚本里，签名不可能覆盖包含它自己的那段数据。

两种可行做法：

- **TxID 不包含整个解锁数据**（见证信息和解锁脚本），解锁数据在区块里另行承诺，类似 Bitcoin SegWit 的 wtxid。推荐这种：解锁区可以保持现在的灵活性。
- TxID 包含解锁脚本，但解锁区收窄为只能压入值，并强制规范编码。这样会失去你想要的灵活性。

这是 Evidcoin 宿主侧的决定，见 Q7。



### P0-7 「资源有限」的论断不成立，限额存在缺口

**问题**

评审时 Design.md 称固定长度脚本的资源消耗有限。但 EACH 的迭代次数取决于集合大小：嵌套 k 层 EACH 遍历 `RANGE[255]` 是 255^k 次；循环中反复 `ADD` 字符串可指数级增长。

缺失的限额：实参区容量、OUTPUT 缓存、EVAL 嵌套深度与 SCRIPT 引用次数（SCRIPT + EVAL 可绕过「EMBED 深度为 0」）、子脚本的 GOTO 次数（只写明顶层主脚本 ≤ 2 次；若子脚本不受此限，深度为 3 时加载次数会急剧放大）、切片/字典的大小如何计入限额、循环体内局部域是否每轮重置（容量 128，且只增不减）。

**影响**

成本预算没有数值。「组队校验冻结机制」全文未定义。成本不影响手续费时，低手续费交易可以占满区块的成本额度。

**建议**

论断改为「必然终止，开销由成本预算约束」。补齐上述限额。成本按实际执行计量，包括外部脚本加载、Merkle 证明验证、正则和 MODEL `...` 搜索。手续费或打包优先级至少与成本挂钩。

**依据**

- `docs/conception/Design.md` 参数限定、执行成本
- `docs/conception/Instruction/2.截取指令.md` 局部域容量 128

#### 回答

循环体内的局部域肯定各自独立，因此对于同级局部域，后面的迭代可以覆盖（清除）前面的创建。此时局部域的信息如果要保留，需要压入数据栈才对。没有办法在后续的迭代块里引用之前的局部域，所以覆盖是安全的。

对于其它资源限制，我想请你提出具体的建议。还有关于成本函数，应该怎么创建呢？希望听到您的指导意见（可以稍微详尽一些）。

手续费关联打包优先级，成本高的脚本肯定应该支付更多的费用，但这应该只是一个共约。铸造者是随机的，它们有自己的选择权。如果过低交易费交易滞留内存池，240 个区块后它们会过期（被丢弃）。约束交易支付足够的手续费，是靠区块容量限制和过期规则来完成。

组队校验的**冻结**是指首领校验（仅验证交易中首项输入，协助实现快速广播。对首领输入有确定性约束）中，首领校验通过但后续对交易完整验证时失败，则对该首领输入加入黑名单，临时冻结）。与脚本自身的逻辑无关。

#### 评审回复

循环体的局部域每轮独立：同意。写进 Spec 时统一为「每次进入一个块都新建空的局部域」，包括每一轮迭代、每个 CASE、MAP / FILTER 的每次调用。

下面是限额与成本函数的建议。数值都是初始建议，需要先用基准测试校准，再冻结。

**一、硬限额（共识规则，超出即失败）**

现有的保留：栈高 < 256；解锁、锁定脚本各 < 8KB；EMBED ≤ 4 次且深度为 0；GOTO 每个脚本 ≤ 2 次、深度 ≤ 3。补充：


| 项目        | 建议上限     | 说明                                                                                                        |
| --------- | -------- | --------------------------------------------------------------------------------------------------------- |
| 实参区条目     | < 256    | 与栈高一致                                                                                                     |
| 块嵌套深度     | ≤ 32     | 限制解释器的递归深度。表达式受 255 字节约束，不必另设                                                                             |
| 集合成员数     | ≤ 1024   | 切片、字典均适用                                                                                                  |
| EVAL 嵌套深度 | ≤ 3      | EVAL 的代码里还可以有 EVAL                                                                                        |
| 外部脚本加载总数  | ≤ 8 / 输入 | GOTO、EMBED、SCRIPT 合计，包括子脚本和 EVAL 代码中的加载。按现有规则，深度 3、每层 2 次 GOTO 最多 14 个子脚本，每个脚本还能 EMBED 4 次，单个输入的加载可达 74 次 |
| OUTPUT 缓存 | 无共识限额    | 公共节点上是空操作；私有节点自行限制                                                                                        |

> **作者提议：**
> 1. 嵌套深度感觉可以更严一些，比如小于等于 20 或 16。请你斟酌。
> 2. 禁止 EVAL 嵌套，即：EVAL 中不能再包含 EVAL。
> 3. 实参区条目可以放宽一点，比如数据栈容纳不下，可以籍由实参区变通。考虑与集合成员数限额一致。

局部域 128 / 块、全局变量 256 槽已有，不变。

**单项大小上限需要重新核对**（Q8）。现有「栈数据项 < 4KB」有两处冲突：

- `SOURCE[0x80]`、`IN{Source}` 返回解锁加锁定的完整字节码，最长约 16KB；`IN{Locked}`、`OUT{n, Locked}`、`SCRIPT` 最长 8KB。都会超过 4KB。
- 后量子签名：ML-DSA-87 的签名是 4627 字节，超过 4KB；SLH-DSA 的签名在 7.8KB 到 49KB 之间。如果 Evidcoin 允许定制验证使用这类算法，签名作为栈数据项放不下。多签时 3 个 ML-DSA-65 签名（每个 3309 字节）合计约 9.9KB，也超过解锁脚本的 8KB。

建议：普通数据项的上限按 Evidcoin 实际采用的签名算法确定，至少能放下一个签名或一个公钥；Script 类值和源码类取值单独设上限 16KB。

**二、成本函数**

Design.md 已有的原则不变：成本是指令性质与实参大小的确定性函数，与硬件无关。在此之上补三条规则：

1. **每条被执行的指令至少计 1 个单位**（基础分派成本），包括公共节点上作为空操作的 `PRINT`、`OUTPUT`。否则零成本的指令放进循环里可以被无限放大。
2. **新分配的数据按字节计成本**：每产生 64 字节新数据计 1 个单位。这样单个输入的成本预算同时也限制了内存总量（预算 10 万单位时，累计分配不超过约 6.4MB），不需要再单独做内存计量。
3. **跳过的代码不计执行成本**，但加载期的结构扫描按脚本总长度计费。

公式的形状是 `cost = 1 + 按字节项 + 按成员项 + 特殊项`。各类指令的初始建议：


| 类别                                                         | 成本                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 值、截取、栈操作、比较、逻辑、`ENV` / `IN` / `OUT` 取值      | 1 + 涉及条目数 + ⌈新数据字节 / 64⌉                           |
| 集合操作（`MERGE`、`REVERSE`、`SPREAD`、`ANYS`、`EVERY` 等） | 1 + 成员数 + ⌈新数据字节 / 64⌉                               |
| Int 运算                                                     | 2                                                            |
| BigInt 运算                                                  | 加减与位运算：2 + w；乘、除、模、幂：2 + w²（w 为操作数的 64 位字数，最多 16） |
| 字符串、字节的拼接与转换                                     | 1 + ⌈结果字节 / 64⌉                                          |
| 哈希                                                         | 20 + ⌈输入字节 / 64⌉ × k（k 按算法校准，BLAKE3 约 1，SHA3 约 3） |
| `FN_BASE58`、`FN_ADDRESS`                                    | Base58 编解码的耗时与长度的平方成正比。建议限制输入 ≤ 256 字节，或按长度平方计费 |
| 签名验证                                                     | 每个签名按实际算法校准，量级约 1000                          |
| 正则                                                         | 编译：10 + 模式字节；匹配：⌈输入字节 × 模式字节 / 8⌉（按 Go 正则最坏情况与「输入 × 模式」成正比估算） |
| `MODEL`                                                      | 10 + 每次指令比较 1；`...` 的每一次尝试都计入                |
| `EACH`                                                       | 每轮 1。`MAP` / `FILTER` 每轮 2，另加建域 5                  |
| `EVAL`                                                       | 10 + ⌈代码字节 / 64⌉                                         |
| 外部加载（GOTO、EMBED、SCRIPT）                              | 固定 200 + ⌈脚本字节 / 64⌉。不论默克尔证明由用户携带还是节点自取，成本相同（见 P1-6 回复） |
| 加载期结构扫描                                               | ⌈脚本字节 / 64⌉                                              |


**预算**

- 校准方法：在参考硬件上跑基准，定出 1 个单位约等于多少纳秒。预算 = 目标最长验证时间 ÷ 单位耗时。
- 初始建议：`MaxInputScriptCost` 为 100,000，`MaxTxScriptCost` 为 1,000,000，`MaxBlockScriptCost` 为 50,000,000。按 1 单位约 100 纳秒估算，分别约为 10 毫秒、100 毫秒、5 秒（单核计；不同输入之间可以并行验证）。
- 对照：一次标准单签 `SYS_CHKPASS` 约 1,000–2,000 单位；三层嵌套的 `EACH` 各遍历 255 项需要 1,600 万单位以上，会被单个输入的预算直接拦下。

三层预算都是共识规则。区块的成本是区块内所有输入实际执行成本之和。

> **作者提议：**
> Evidcoin 区块链系统是固定6分钟出一个区块，每区块最少可容纳交易1万笔以上。
> 因此这里的区块成本应当可由应用自己配置，比如这里的 `50兆/5s` 至少可乘以 10。
>
> 每输入和每交易的成本上限与宿主区块链设计关系不大，同意你的预算建议。

**三、手续费**

同意不在共识层把手续费和成本挂钩，由铸造者自行选择。

建议在节点的转发策略（非共识）里补一点：交易被收录之前，节点已经付出了验证成本，而验证失败的交易不付任何费用。节点可以：

- 按「手续费 ÷ max(交易字节数, 成本折算的字节数)」排序转发和打包，类似 Bitcoin 把签名操作数折算进虚拟大小；
- 对频繁转发验证失败交易的对等节点降低信任。

> **作者回复**：同意此建议。



### P0-8 解锁段遗留的实参区与局部域会带入锁定段（第二轮新增）

**问题**

解锁区 `[0-45]` 包含截取指令 `@`、`&`。解锁脚本与锁定脚本在同一个脚本域里连续执行，数据栈、实参区和顶层局部域都是共用的（`SOURCE` 的说明也写明「脚本顶层的块域包含解锁脚本」）。实参区的规则是「有值则必须恰好 n 项、一次取完」，于是解锁脚本可以预先放入恰好 n 个值，锁定脚本中第一条需要实参的指令就会使用花费者给的值，而不是锁定脚本自己算出的值。

**影响**

以 P1-5 回答中的「链间兑换」脚本为例。甲是退款方，持有位置 0 的签名权。甲在到期之前用下面的解锁脚本花费：

```go
// 解锁脚本（甲）：
@{1} @{0}                           // 实参区：[1, 0]

// 锁定脚本（节选）：
SYS_CHKPASS                         // 无实参，不读实参区；甲的签名验证通过
ENV{Height} {<expireHeight>} GT     // GT 取实参区的 [1, 0]：1 > 0 => true
IF{                                 // 从栈顶取到 true
    SIGNED[0]                       // 甲已签名
    PASS                            // 通过（甲赎回）
    EXIT
}
```

`ENV{Height}` 和 `{<expireHeight>}` 都不取实参，返回值入栈；`GT` 是第一条取实参的指令，此时实参区非空且恰好 2 项，于是比较的是 `1 > 0`。甲可以在任何时候赎回，哈希时间锁失效：甲可以先在另一条链上用原像领取乙的币，再立即收回自己的币。

同类问题：任何「时间判断在前」的脚本（储蓄锁、遗嘱）、任何开头就用 `IF` 分支的脚本，花费者都能改写第一个判断。局部域也一样：锁定脚本若用 `&[0]` 取自己存入的第一个值，解锁脚本只要先存入一个值，下标就会错位。

**建议**

解锁段与锁定段之间只共享数据栈：

- 解锁段结束时，实参区必须为空，否则验证失败；
- 锁定脚本从一个新的顶层局部域开始，解锁段的局部域丢弃；
- `SOURCE` 的取码视图不受影响，仍可以把「解锁 + 锁定」当作一段源码提取。

Bitcoin 在 2010 年遇到过同类问题，修复方式也是把 scriptSig 与 scriptPubKey 分开执行、只共享栈。

**依据**

- `docs/conception/Design.md` 实参空间、解锁数据
- `docs/conception/Instruction/2.截取指令.md`
- `docs/conception/Instruction/13.环境指令.md` SOURCE：「脚本顶层的块域包含解锁脚本」



#### 回答

这确实是一个被我忽略的问题，解锁段的实参可以跨过锁定段无需实参的指令序列。

这个脚本也可以视为一个编码漏洞，修复很简单：`@ENV{Height} @{<expireHeight>} GT`，或 `ENV{Height} {<expireHeight>} @POPS[2] GT`，它们都会抑制上面的解锁构造。或者在 `EVN{Height}` 前置一个 `NOP` 预防性清空实参区也行。但这确实是一个容易导致漏洞的点。

允许解锁段设置局部域延续到后续的锁定脚本，曾是我期望的能力，它可以提供更多的灵活性。但局部域实际上也有实参区类似的问题：解锁段可以改变局部域存值的堆叠（影响序号），所以它也应当像实参区一样被谨慎对待。

从锁定脚本的编写角度看，栈条目的引用实际上非常灵活，因此只考虑数据栈共享是可行的（表达能力足够）。而且也可以让编写脚本时更少顾虑——只需要关注数据栈上的值即可。因此，感谢你提出这个问题！同意您的建议。



## P1 语义缺口



### P1-1 类型系统与数值语义未定义

**问题**

跨类型比较与运算（Int / Byte / Float 混用）没有规则。整数溢出（ADD、MUL、NEG、LMOV）、除零、负数移位未定义。BigInt 有字面量，却没有对应的算术指令。Bytes 与 []Byte 是否同一类型、能否 SLICE / INDEX / SIZE 不明确。BOOL 的转换表不接受 Float，而 FILTER 示例对表达式结果用了 `@BOOL`。BYTE 的「小于 256」会放行负数。RUNE 没有排除代理区。BYTES(BigInt) 丢失符号，BIGINT(Bytes) 只按无符号还原。PACK 的「基础二进制形态」未定义，用于哈希承诺时会出现实现分歧。

**建议**

写一张「运算 × 类型 → 结果或失败」的矩阵。默认：类型不匹配即失败，溢出即失败。

**依据**

- `docs/conception/Instruction/9.运算指令.md`
- `docs/conception/Instruction/8.转换指令.md`
- `docs/conception/Instruction/4.集合指令.md` 的 PACK
- `docs/conception/Instruction/14.工具指令.md` 的 FILTER 示例



#### 回答

Bytes 应该是 []Byte 的别名，可以 SLICE/INDEX/SIZE。

FILTER 循环块里实际上处理的是整数，因此可以直接 `@BOOL`。不过因为浮点数零值可以精确表示，所以我添加了浮点数转布尔值的支持。

BYTE 的范围是 `[0-255]`，应当存储为一个字节值（小整数）。已修订基本的运算指令支持 BigInt（如果后期必要，可创建独立的模块完整支持）。

BigInt 到 BYTES 的相互转换会丢失符号位，这是一个固有的缺点。只能是提醒用户注意。两者的互转只是为了提供某种便捷，不承诺完美。

> **提示：**
> 曾考虑将 BitInt 的附参也编码进 BYTES，但这样似乎并不恰当。

本条目的其它问题，你可以按照自己的想法完善，遵循通行的行业习惯即可。

#### 评审回复

已确认的部分记录在案：Bytes 即 `[]Byte`；Float 可转布尔；BYTE 范围 `[0, 255]`；基本运算支持 BigInt；BigInt 与 Bytes 互转丢失符号。

其余按通行做法补齐如下，主要参照 Go 的语义。写入 Spec 时整理成一张「运算 × 类型」表。

**数值提升**

- 整数类按 Byte → Rune → Int → BigInt 提升。Byte、Rune 参与算术时先提升为 Int，结果至少是 Int。这与 C 的整数提升相同，可以避免字节运算的回绕问题。
- 有 BigInt 参与时结果为 BigInt，不会自动降回 Int。BigInt 结果超过 1016 位（字面量能表达的上限）即失败，这样运行时的任何 BigInt 都能写回字面量。
- 表达式 `()` 的结果：Int；有 BigInt 操作数时为 BigInt；私有域里还可能是 Float。
- Bool、String、Bytes、nil 不是数值，参与算术即失败（`ADD` 的拼接除外）。

**溢出与异常**（一律失败）

- Int 的加、减、乘、取负、幂溢出即失败。Go 本身是静默回绕的：我在本机验证过，`MinInt64 / -1` 的结果仍是 `MinInt64`，`-MinInt64` 也还是 `MinInt64`，所以实现必须显式检查。
- 除数或模数为零即失败。
- 除法向零截断，余数的符号与被除数相同（同 Go）。
- `POW` 的指数为负即失败；`0^0 = 1`。
- 移位：Int 的移位数必须在 `[0, 63]` 之内，否则失败。左移移出的位直接丢弃（位运算不做溢出检查，同 Go）；右移为算术右移。BigInt 左移的结果超过 1016 位即失败。
- 位运算对负数按二进制补码处理（Go 的 `big.Int` 也是这样定义的）。

**比较**

- `EQUAL` / `NEQUAL`：数值类先提升再按值比较（Byte 65 等于 Int 65）；String 与 String、Bytes 与 Bytes 按字节比较；Time 按时刻比较。两边类别不同时结果为「不相等」，不失败；nil 只等于 nil。切片与字典不可比较，比较即失败。这与 Go 比较两个 `any` 值的行为一致。
- `LT` / `LTE` / `GT` / `GTE`：只用于数值、String、Bytes、Time，且两边类别相同，否则失败。

**拼接与合并**

- `ADD` 只允许 String + String、Bytes + Bytes，混用即失败；结果受单项大小上限约束。
- 字典合并返回一个新字典：先保留左侧的键及其顺序，右侧新增的键按其顺序追加，重复的键取右侧的值。

**转换补充**

- `RUNE`：代理区 `0xD800–0xDFFF` 失败。
- `INT(String)` 解析失败即失败。
- `BOOL` 不接受切片、字典、Bytes（判空用 `SIZE BOOL`）。
- `BYTES(Int)` 为 8 字节大端补码。可选：补一个对称的 `INT(Bytes)`，要求恰好 8 字节，按大端补码还原。
- 建议补 `BYTES(Bool)`：`false` 为 `0x00`，`true` 为 `0x01`，供 PACK 使用。

**PACK**

建议直接定义为「每个成员做 `BYTES` 转换，再首尾相接」，不另设一套「基础二进制形态」，这样只需要维护一张转换表。成员不能转为 Bytes 时失败。

需要提醒一点：PACK 的结果不带长度信息，`["ab", "c"]` 与 `["a", "bc"]` 的打包结果相同。用于哈希承诺时，如果成员长度可变，应先固定长度，或自己加入长度字段。

**SLICE 与字符串**

建议 `SLICE` 只用于切片和 Bytes，对 String 使用即失败，以免切断 UTF-8 字符；字符串截取用 `SUBSTR`。



### P1-2 错误处理口径不统一

**问题**

SLICE、POPS 越界即失败。SUBSTR 长度不足返回空串。ITEM 缺键返回 nil。`$[n]` 越界返回 nil。MAP 静默丢弃 nil 结果。同类异常分别表现为失败、空值或静默忽略。

**建议**

统一为「异常即脚本失败」。确实需要容错的场景提供显式的变体指令。

**依据**

- `docs/conception/Instruction/4.集合指令.md` SLICE
- `docs/conception/Instruction/14.工具指令.md` SUBSTR、MAP
- `docs/conception/Instruction/12.模式指令.md` 正则取值越界



#### 回答

SUBSTR 长度不足的问题，已经修改为返回已提取的部分（这样更合理）。

SLICE/POPS 越界是明显的编码时问题，因此应当失败。其它几个返回 nil 的状况，是一种必要的友好。

#### 评审回复

接受。现有的处理可以归纳成一条容易记的原则，也与 Go 一致：

- **按位置访问，越界即失败**（同 Go 的切片越界）：`SLICE`、`INDEX`、`POPS`、`PEEK`、`PEEKS`、`VIEW`、`&[n]`。
- **按键查找，缺失返回 nil**（同 Go 从 map 取不存在的键得到零值）：`ITEM`。
- **明确声明的宽松行为**：`SUBSTR` 返回已截取的部分；MODEL 内 `$[n]` 越界返回 nil；`MAP` 丢弃 nil 结果。

`INDEX` 越界的行为目前文档没写，按这条原则应为失败。Spec 里每条指令会有一行「异常」，写明属于哪一类。

nil 流入后续指令时：参与算术即失败；`BOOL(nil)` 为 false；`EQUAL` 只与 nil 相等。



### P1-3 控制流与作用域的边界情况未定义

**问题**

EVAL 写的是「通关状态与调用层无关」，同时又写「失败会传递出来」：EVAL 内 `PASS(false)` 到底终止谁？MAP / FILTER 内的 PASS、GOTO、EXIT 有什么效果？CASE 里的 BREAK / CONTINUE 作用于 SWITCH 还是外层 EACH？EACH 遍历字典时，循环体执行 SET / DEL 会怎样？`IF{} IF{} ELSE{} ELSE{}` 是编译期非法还是运行时忽略？`SYS_NULL` 的 NULL 点按字节位置还是按执行记录？环境指令里有的示例只有按位置解释才成立，游标描述又更像运行时记录。

**建议**

为每个块类指令写一张「块内可用指令 + 对外部状态的影响」表。NULL 点明确为静态位置。

**依据**

- `docs/conception/Instruction/14.工具指令.md` EVAL
- `docs/conception/Instruction/7.流程控制.md` IF / ELSE
- `docs/conception/Instruction/13.环境指令.md` SOURCE 与 NULL 点



#### 回答

EVAL 是在一个独立环境域中执行，其中的 PASS(false) 只是该环境域的正常结束，不是失败。内部的失败需要抛到外层调用者，连带外层也失败并退出。

MAP / FILTER 内部的代码是在一个私有块域执行，其中的 PASS/CHECK 依然属于当前脚本域，因此子块中的 PASS(false) 会传递出来，当前脚本通关失败并终止。又因为 PASS(false) 会向上透传，所以如果它在一个子脚本中，也依然会导致整个验证不通过。

GOTO 子脚本是独立的脚本域（与私有块域不同，全局变量区也独立），其中的 PASS 属于脚本域状态，但 PASS(false) 会透传，导致调用者通关失败并结束整个验证。EXIT 也属于脚本域，子脚本里的 EXIT 结束子脚本本身。**注**：MAP/FILTER 私有块域里的 EXIT 会结束其所在脚本（而非退出块域）。

CASE 里的 BREAK 对 EACH/SWITCH 都有效，退出最近的一个逻辑/语法块。CONTINUE 只作用于 EACH 循环逻辑，不适用于 SWITCH 指令。这些都是 Go 语言里的普通逻辑。**注：**本脚本语法主要借鉴 Go 和 JavaScript 语言。

EACH 遍历字典时，字典本身为引用，所以会在各个循环里修改共同的对象。结果也会体现到循环外层的初始引用（只要它们操作的是同一个对象）。

IF/ELSE 的平级没有嵌套逻辑，因此非法嵌套就是一种错误。交易中的脚本是编译成字节码之后的数据（非文本源码），但是在文本编译为字节码的编译期限制是没有用的，用户完全可以构建一个语法不正确的输出脚本（输出脚本在花费前不会尝试检查或执行）。所以只能是执行期（运行时）非法。

SYS_NULL 的 NULL 点是按字节位置计算，游标只是一个「越过位置……」的比喻，不是严格意义上的执行步进。

#### 评审回复

BREAK / CONTINUE 按 Go 处理、非法的 IF / ELSE 在执行期失败（另见 P1-8 回复中加载期校验的建议）、NULL 点按字节位置，都同意。

Spec 里会把这些写成一张「执行上下文 × 指令」表。


| 在哪里执行         | `PASS(false)`         | `EXIT`                 | `END` / `INPUT`（公共节点） | 运行错误       |
| ------------------ | --------------------- | ---------------------- | --------------------------- | -------------- |
| 顶层（解锁 + 锁定）| 结束，不通过          | 结束，按状态判定       | 结束，按状态判定            | 失败           |
| EMBED 嵌入的代码   | 同顶层                | 同顶层                 | 同顶层                      | 失败           |
| GOTO 目标脚本      | 不通过透传，结束      | 结束子脚本，回到调用者 | 同顶层                      | 失败           |
| MAP / FILTER 体内  | 结束整个脚本，不通过  | 同顶层                 | 同顶层                      | 失败           |
| EVAL 的代码        | 结束 EVAL，调用者继续 | 结束 EVAL，回到调用者  | 同 EXIT（公共域也被封装）   | 向外传递，失败 |

> 作者修订：
> - 原评审回复里提出的几个问题已经移除。
> - 这几个问题已经在 Conception 中修订吸收，上面的表格也根据修订进行了修改。
> - EVAL 中的公共域退出不影响调用者的公共域逻辑，因为 EVAL 的独立环境也封装了公共域。



### P1-4 表达式 () 的字节码形式未定义

**问题**

中缀表达式编译成字节码后，运行时是再做优先级解析，还是已经转成后缀形式？表达式内允许哪些指令？`POP` 会修改数据栈，与「表达式内没有存入逻辑」不符。命名指令在表达式内从表达式外取参，文档自己也标了「不直观」。

**建议**

规定表达式内部编码为后缀序列，并给出表达式内可用指令的白名单。

**依据**

- `docs/conception/Instruction/9.运算指令.md` 表达式封装，以及 `( 100 + POW )`



#### 回答

表达式内没有存入逻辑指的是 `@`/`&` 截取指令不能用，因为存值指令本身没有返回值，它无法成为一个操作数。实际上表达式的逻辑和其它普遍语言一样：表达式内部可以使用函数，唯一的区别是实参从哪来。

普通表达式里的函数从当前位置传实参，本设计中的栈脚本从实参区或数据栈取实参。但两种表达式都需要函数或指令有一个有效的返回值作为操作数。

POP 只是简单的从数据栈取出操作数，不是特例，因为实际上只要允许表达式内可以使用命名指令，任何命名指令都需要从外部（数据栈/实参区）取实参。它们返回值，并且作为表达式内的唯一例外，返回值被截获为操作数。在表达式外，返回值会自动写入数据栈，截获返回值需要明确的指令（`@`,`&`）。所以在截获返回值规则上，只是改变了「自动入栈」的规则。

虽然在表达式内使用命名指令不直观，但如果不允许使用，那就像在普通语言中，表达式内不能使用函数一样，更不合理。

哪些指令可以用在表达式内，其实只需要一条规则：*该指令可以返回合法的操作数即可*，不需要明确清单，不能返回合法操作数的自然失败。

> **提示：**
> 用户在构造交易的输出脚本时，通常需要本地编译、检查或预执行，以便于发现问题。
> 如果用户编写了错误的输出脚本，该脚本就无法作为下一笔交易的输入正常花费/消费。用户应当自负其责，这是正常的逻辑。

脚本中的表达式需要体现业务逻辑。我不知道预编译为后缀序列之后，当向读者展示脚本时，是否还能反编译恢复为原始样式。如果能，效率如何，简单吗？还是需要复杂的处理？如果答案是否定的，我觉得可能保持原始指令序列更合适（可以探讨：运行时即时解析处理成本高吗？）。

#### 评审回复

同意保留中缀形式的字节码，不改成后缀序列。回答你的三个问题：

- **后缀序列能否还原？** 能。用一个栈把后缀序列重建成表达式树，再按优先级输出最少的括号，是线性时间的标准算法，几十行代码。但多余的括号会丢失，例如 `(a + (b * c))` 会显示成 `a + b * c`，不能逐字还原原文。
- **运行时解析的成本：** 表达式最长 255 字节，按优先级解析（如调度场算法）是线性时间，耗时在微秒以下；一次签名验证需要几十到上百微秒。解析成本可以忽略。
- **更好的做法：** 链上存中缀，便于展示，也便于 MODEL 按原样匹配表达式；实现可以在加载期把表达式转成内存里的后缀形式再执行（见 P1-8 回复）。这只是实现层的优化，不改变链上格式。

保留中缀，Spec 需要补齐的规则：

1. 文法：`*` `/` `%` 优先于 `+` `-`，同级左结合。一元 `+` / `-` 出现在表达式开头、运算符之后或左括号之后，优先级最高。
2. 操作数：值指令、子表达式，或任何恰好返回 1 个值的指令（就是你说的那条规则）。返回 0 个或多个值（如 `DIVMOD`、`POPS`）即失败。
3. **求值顺序：操作数严格按书写顺序从左到右求值，与优先级无关。** 这条必须写明，因为操作数可能有副作用：`( POP - POP )` 的结果取决于哪个 `POP` 先执行。
4. 表达式内不允许截取前缀 `@`、`&`（存值）、`_`；局域取值 `&[n]` 是取值指令，可以作为操作数；`~` 可以使用，用来改变操作数指令的取参渠道。
5. `9.运算指令.md` 开头「命名指令用于表达式外，不可混用」与此冲突，建议改为「运算符号只能用于表达式内；命名指令在表达式内作为操作数使用」。



### P1-5 依赖区块时间/高度的条件不单调

**问题**

`ENV{BlockTime}`、`ENV{Height}` 指「即将打包进入的区块」，内存池验证时并不确定。「在高度 X 之前有效」会让交易在内存池里过期，链重组后也可能失效。矿工还能在一定范围内操纵区块时间。Bitcoin 只允许「不早于」类时间锁，就是为了避免这个问题。

**建议**

只提供单调的「不早于」比较（类似 CLTV / CSV），或明确这类交易在内存池与重组时的处理规则。

**依据**

- `docs/conception/Instruction/13.环境指令.md` BlockTime、Height

#### 回答

在 Evidcoin 中，矿工无法操纵区块时间戳（实际上区块里没有时间戳，只有高度。区块时间戳按固定 6 分钟间隔计算而来）。

在 Evidcoin 中，「不早于」和「不晚于」的时间结构都是允许的，过期的问题由用户自己负责。分叉重组会使得从失败分叉上回收的交易的时间出现延宕，但是有 21 个区块不再回收的逻辑（超出竞争链段长度）。所以过期失效是有限度的——用户需要预先评估分叉的风险并合理安排时间约束。过期赎回的逻辑在本脚本系统中很容易表达，因此与 Bitcion 有较大的不同。脚本需要有完整的逻辑表达能力。

**用例：链间兑换**

```go
// 锁定脚本
SYS_CHKPASS                         // 内置验证（从环境读取实参）
ENV{Height} {<expireHeight>} GT     // 是否过期
IF{                                 // 是：
    SIGNED[0]                       // 是否由甲签名，返回Bool
    PASS                            // 栈顶为真时通过（甲赎回）
    EXIT                            // 结束脚本
}                                   // 否：
SIGNED[1] PASS                      // 是否由乙签名，真时通过
FN_HASH256                          // 栈顶剩余项为<hashSource>，计算哈希
DATA{<hashResult>}                  // 预置哈希结果（哈希屏障）
EQUAL PASS                          // 栈顶两个序列相等比较，真时通过（乙转出）
```

确实，如果脚本逻辑设计错误，一笔输出可能永远无法花费。但在 Bitcion 中，矿工也不会阻止脚本输出到一个无法使用的地址吧？编写正确的脚本应当是用户的责任，系统不应该涉入。并且在 Evidcoin 中，UTXO 集有末端指纹的状态确定性，不需要从创始区块开始计算全链的 UTXO 集。

> **提示：**
> Evidcoin 中可以从链末端逆向验证 UTXO 集，安全性通过足够长度来认可。

另外，交易在内存池里过期有两种情况：

1. 脚本本身无法执行通过，执行逻辑上已经过期。这种会导致其输出项永久在 UTXO 中。
2. 脚本本身没有过期问题，但是区块一直没有收录它。Evidcoin 中该笔交易会在 240 个区块之后过期。用户可以重新构建交易花费它。



#### 评审回复

接受。Evidcoin 没有可被操纵的时间戳；「不早于」「不晚于」都允许；过期风险由用户评估。这些都成立，脚本需要完整的表达能力也同意。

需要在实现层（宿主侧）补一条：交易的有效性可能随高度变化，内存池要在每个新区块之后重新验证这类交易。可以让虚拟机在执行时记录「本次执行读取过 Height / BlockTime / TipHeight」，只对带这个标记的交易重验。

### P1-6 外部引用的数据可用性

**问题**

GOTO、EMBED、SCRIPT、INOUT、XFROM 都依赖历史交易数据，而系统又鼓励剪枝。节点取不到数据时，结果是「拒绝」还是「暂不判定」没有定义。如果是拒绝，节点之间会因缓存不同而出现分歧。

**建议**

规定「无法获取数据 ≠ 验证失败」。用户附带的 Merkle 证明计入成本。明确节点必须保留的最小状态（区块头、输出承诺）。

**依据**

- `docs/conception/Instruction/AGENTS.md` 历史交易的携带与缓存
- `docs/conception/Instruction/15.系统指令.md` 见证数据与剪枝



#### 回答

系统剪枝只是针对见证信息（主要是后量子算法的签名数据太大）。用户可以携带哈希路径证明，因此实际上问题不大。

无法获取数据当然不属于验证失败，最终区块确定后，同步区块时，那些缺失的数据会被同步。如果是无法获取数据的节点打包区块，那些无法完成验证的交易也就不会进入区块。这不会带来问题。

用户附带的 Merkle 证明其实反而不应该进入成本，不然它们会尽可能逃避携带证明，反而使得验证节点更依赖公共服务器（Evidcoin/Blockqs）了。

相比于抗量子签名，Merkle 证明的数据量并不大，忽略它的成本是可行的。

> **提示：**
> Evidcoin 中的输出项集本身会用默克尔树构建，且输出项中的子项也采用了摘要哈希设计。
> 我觉得不需要在脚本侧规定太详细的应用端要求，应用端应自己想办法满足规格。



#### 评审回复

接受。「取不到数据不等于验证失败」需要在虚拟机的返回结果里体现出来：执行结果除了通过、失败，还要有第三种「数据不可用」。这样宿主知道应该稍后重试，而不是丢弃交易，或惩罚转发它的节点。

关于默克尔证明的成本，你的顾虑是对的：如果携带证明要多付成本，用户就会倾向于不带。建议的折中是：**外部脚本加载按固定成本计**（P0-7 回复表中的「固定 200 + 按字节」），不论证明是用户带来的还是节点自己查到的。这样带不带证明不影响成本，只影响验证速度，你原来设计的激励（带证明的交易更快被收录）不变；节点验证证明的实际开销也有了对应的成本。

一个可选的优化：GOTO、EMBED、SCRIPT 的目标都写在附参里，是静态的。宿主可以在执行前扫描字节码，预先取齐所有外部脚本。



### P1-7 动态调用面与升级机制

**问题**

CALL 按字符串方法名分派。评审时文档写明方法数量没有限制、安全性由实现保证，等于共识面由实现决定，每加一个方法就是一次共识变更。FN_X / FN_XX / EXT_MO 的索引表没有注册与版本规则。遇到未使用的码位，是失败还是保留为成功（类似 OP_SUCCESS 的软分叉）没有决定。脚本没有版本号。

**建议**

引入脚本版本字节。模块方法表随版本冻结，包含签名、参数类型转换与成本。明确未用码位的处理策略。

**依据**

- `docs/conception/Instruction/14.工具指令.md` CALL
- `docs/conception/Instruction/16.函数指令.md`、`17.模块指令.md`、`18.扩展指令.md`

#### 回答

「文档写明方法数量没有限制、安全性由实现保证」是一种逻辑表达，不是规格要求。未使用的码位处理方式可以沿用 Bitcoin 中 OP_SUCCESS 的软分叉逻辑，挺好的！

同意你的建议，请你根据你的判断设计上面问题相关的事宜。

#### 评审回复

按你的授权，建议如下。

**1. 版本号**

- 每个锁定脚本有一个版本号，由创建输出的人决定，花费者不能选择。解锁脚本按它对应的锁定脚本的版本执行。
- 版本号放在宿主的输出结构里，不放进脚本字节码。对 Evidcoin，如果输出项配置字节的高 4 位尚未占用（低 4 位已用于验证类别），可以用它；否则用一个独立字段。见 Q6。
- GOTO、EMBED、SCRIPT 引入的脚本，按它们自己所在输出的版本执行，因为它们是按那个版本编写的。

**2. 一个版本冻结哪些内容**

每个版本对应一组不可变的表：指令码表（含附参格式）；`GVAL` / `ENV` / `IN` / `OUT` / `INOUT` / `XFROM` 的字段表；`FN_X` / `FN_XX` / `EXT_MO` 的索引表；各模块和对象的方法表（方法名、参数类型、返回类型、成本函数）；成本表；限额。新版本只能新增，不修改旧版本的任何一项。

**3. 未分配码位：沿用 OP_SUCCESS**

- 节点在执行前扫描锁定脚本（以及 GOTO、EMBED 引入的脚本）。遇到当前版本未分配的指令码，或 `FN_X`、`FN_XX`、`EXT_MO`、`GVAL`、`ENV` 等指令中未分配的索引，该脚本直接判为通过，不再执行。将来给这些码位定义语义时，旧节点仍判通过，新节点执行新规则，属于软分叉。
- 这条规则**只适用于锁定方写的脚本**。解锁脚本和 EVAL 执行的代码里遇到未分配码位，一律失败。否则花费者只要在解锁脚本里、或在交给 EVAL 的 `CODE` 里放一个未分配码位，就能直接通过。
- `254`、`255` 永久保留，遇到即失败，不按 OP_SUCCESS 处理，留作将来的格式扩展。
- 私有专属指令（浮点字面量、`SYS_TIME`、`SHELL`、`*_PRIV`）属于已分配码位，仍按 Design.md 的规则：公共验证执行到即失败。
- 转发策略（非共识）：节点不转发、不打包「创建了含未分配码位的输出」的交易，防止有人误把资金锁进实际上任何人可花费的脚本。

**4. 未知版本**

节点遇到自己不认识的版本号，也按通过处理，这同样是软分叉的入口。转发策略同上。

**5. CALL 的方法名**

方法名是运行时的字符串，无法在执行前扫描，所以 CALL 调用当前版本方法表中没有的方法时失败，不适用 OP_SUCCESS。新增方法需要新版本。

#### 回答

「公共节点上 PRINT / FN_PRINTF / OUTPUT / BUFDUMP 一律为空操作」这条接受，但无需进入成本，因为实际的公共成本几乎为零。

解锁脚本区的指令范围已经收窄，并且已经把原本集合指令区的 `CALL` 移到了解锁无法触及的工具指令区。原值指令 `VALUE` 已经改名为 `GVAL`，并且列出了部分字段。它主要是提供必要的系统级信息的只读输出，辅以脚本版本控制，后期添加字段应该是可控的。

对于「位置限制改为静态检查」，我不清楚你指的是编译期（文本源码 => 指令码），还是执行期的前置优化。如果是前者，这种检查就只是一种便利，无法约束不采用检查的交易构建者。因为最终存储在交易中的脚本，就是指令码字节序列，而不是文本源码。

> **设计：**
> 如果要向人类读者展示交易中的脚本，需要从脚本指令码反编译为文本源码。
> 脚本中指令的设计，已优先考虑了指令码字节序列容易解析和存储（比如块长度附参）。

当然，其实我也想请你评估一下该脚本系统指令码的设计，是否有利于运行时即时解析执行？或者是否还需要一套更优的二进制脚本字节码序列。

> 可能我们需要把概念对齐：
> 在我的意图里，由文本源码解析编译的指令码及其附参和数据，就是脚本中最终存储和运行的字节码序列。



#### 评审回复

公共节点上 `PRINT`、`FN_PRINTF`、`OUTPUT`、`BUFDUMP` 为空操作：同意。补两点：

- 空操作仍要按正常规则消费实参。否则同一个脚本在公共节点和私有节点上的实参区状态不同，后续指令的行为也就不同。
- 成本：不需要专门的成本，但仍按 P0-7 回复计每条指令 1 个单位的基础成本。这不是为打印收费，而是所有被执行的指令都这样计；否则成千上万条零成本指令放进循环里也能拖慢节点。

**「静态检查」指什么**

我说的不是文本编译期，而是**加载期**：每个验证节点拿到字节码后、开始执行之前，先完整扫描一遍。所有节点都做这一步，交易构建者无法绕过，所以它和运行时检查一样有约束力。

这一遍扫描本来就要做：要跳过一个 IF 块，必须先读出块长度。区别只在于扫描时检查多少内容。建议这样分工：

- **加载期**检查结构类规则，这些规则与运行时的值无关：规范编码（P0-6）；块长度与边界；未分配码位（P1-7）；IF / ELSE 的配对；CASE / DEFAULT 只能直接位于 SWITCH 内；模式指令只能位于 MODEL 内；RETURN、BREAK、CONTINUE 必须位于对应的块内；运算符号只能位于表达式内；解锁段只能使用 `[0-45]` 与 `SYS_NULL`。
- **运行时**检查依赖值或执行路径的规则，包括私有专属指令「执行到即失败」。这部分维持你现在的规则。

两种做法的结果不同，需要明确选定一种：只做运行时检查时，一个永远不会执行的分支里有结构错误，这个错误永远不会被发现，脚本照样通过；加载期检查时，整个脚本无效。我建议结构错误一律在加载期判定，这样脚本是否合法只取决于字节码本身，与执行路径无关（Q12）。

**SHELL**

同意它属于私有域。但它意味着任何人发一笔链上交易，就能让所有执行这段脚本的私有节点运行一段 shell 命令。建议在宿主规范里写成强制要求：私有节点默认关闭 SHELL，必须显式配置白名单（例如按脚本哈希，或按签名者授权）才执行。

**字节码是否适合直接解释执行**

适合，不需要第二套二进制格式。概念上与你对齐：文本编译出来的指令码序列（指令码 + 附参 + 关联数据）就是链上存储、也是直接执行的字节码。理由：

- 指令码只有 1 个字节，附参格式由指令码决定，顺序解码即可；
- 块带有长度，条件不满足时可以直接跳过，不必解析块内的内容；
- MODEL、SOURCE 直接作用在同一份字节码上，不需要额外的映射；
- 整体接近 WebAssembly 那种「带显式边界的结构化控制流」，这种形式已被证明适合解释执行。

唯一值得做的是实现层的缓存：加载期扫描时，顺便把指令解码成内存中的数组，记录每条指令的位置、附参、块的结束位置，表达式转成后缀形式。这样 `EACH` 的循环体执行 255 次时就不必重复解码。这份内存结构不属于规格，也不上链。

Spec 需要为此提供一张完整的指令格式表：每个指令码有几个附参，每个附参怎么编码（固定字节数、varint、48 字节等），有没有关联数据，关联数据的长度由哪个附参给出。

### P2-1 「通用化」目标与 Evidcoin 专有概念耦合

**问题**

币金、凭信、存证、`SYS_AWARD` 兑奖槽、`SYS_CHKPASS`、IN/OUT 中的 Creator / Title / Attachment、「年度 + 48 字节 TxID」寻址、「每天 240 个区块」，都是 Evidcoin 专有概念。README 的定位是从 Evidcoin 剥离出来，方便通用化使用。

**建议**

拆成核心 VM（值、栈、实参区、控制流、模式匹配）和宿主接口（ENV / IN / OUT、签名验证、外部脚本加载）。Evidcoin 作为第一个宿主实现。这一决定会决定后续 Spec 的写法。

**依据**

- `README.md`
- `docs/conception/Instruction/15.系统指令.md` SYS_AWARD
- `docs/conception/Instruction/10.比较指令.md` 每天 240 个区块



#### 回答

我想了解一下拆成「核心VM + 宿主接口」的具体细节，对宿主的性能影响如何。

我们可以讨论一下，原则上支持你的策略。

#### 评审回复

**拆分方式**

核心 VM 是一个纯粹的执行引擎：输入「字节码 + 宿主提供的环境」，输出「结果 + 成本」，内部没有 I/O，也不知道 Evidcoin 的存在。

- **核心**：值类型与编码；解码与加载期校验；数据栈、实参区、局域与全局域；控制流与表达式；运算、比较、逻辑、转换；集合；MODEL；EVAL；成本计量与限额；通关状态机；版本门控。
- **宿主接口**：环境字段（`GVAL` / `ENV` / `IN` / `OUT` / `INOUT` / `XFROM` 的字段表由宿主定义）；外部脚本加载（GOTO、EMBED、SCRIPT 的引用格式与取数）；签名验证（`FN_CHECKSIG`、`FN_MCHECKSIG`、`SYS_CHKPASS`，以及供 `SIGNED` 查询的验证记录）；宿主专属的系统指令（`SYS_AWARD`）；私有域通道（`INPUT` / `OUTPUT` / `BUFDUMP` / `PRINT`、`SYS_TIME`、`SHELL`、`*_PRIV`）。
- **Evidcoin 作为第一个宿主实现（Host Profile）**：定义上述字段表、引用格式（「年度 + 48 字节 TxID + 序位」）、签名算法和各项参数（如每天 240 个区块）。

指令码的编号不变，只是规格中把一部分指令的语义标为「由宿主定义」。换一个没有 `SYS_AWARD` 的宿主，该码位对它来说就是未分配码位（按 P1-7 的规则处理）。

Go 中的形态大致如下（示意）：

```go
// 宿主接口：只承载粗粒度、低频的操作
type Host interface {
    LoadScript(ref []byte) (code []byte, ver uint8, err error)  // GOTO / EMBED / SCRIPT；ref 格式由宿主定义；取不到时返回 ErrUnavailable
    VerifySig(req SigRequest) (bool, error)                     // FN_CHECKSIG / FN_MCHECKSIG / SYS_CHKPASS
    SysCall(op byte, aux []byte, args []Value) ([]Value, error) // SYS_AWARD 等宿主专属指令
}

// 环境快照：执行前由宿主一次性填好，按附参索引直接取值
type Env struct {
    GVal, Env, In, XFrom [256]Value
    Outs, InOuts         []OutputView
}
```

**对性能的影响**

可以忽略：

- 热路径（栈操作、运算、控制流、MODEL）全部在核心内部，不经过接口。
- 环境字段由宿主在执行前一次性填进结构体，按附参下标取值是数组访问，不是接口调用。
- 只有加载外部脚本、验证签名、系统调用这类粗粒度操作才走接口。Go 的接口调用开销是纳秒级，一次签名验证则是几十到上百微秒，接口开销不到千分之一。

真正的代价在工程组织上：Spec 要分成「核心规格」和「Evidcoin 宿主规格」两部分来写。好处是核心可以单独做测试向量，宿主的变化不影响核心。

### P2-4 文本语法存在歧义

**问题**

评审时，`${100}`（存值）与提议中的 `${POP}`（按名取值）冲突。`''` 对应两个码位，`{}` 对应整数 / 大整数 / 浮点，`>{}` 对应两种范围匹配，`_` 对应单指令通配和指令段通配，`?` 同时出现在多个模式指令里。MODEL 中的 `^{?}` 试图跨码位匹配。

**建议**

写出正式文法，并规定「文本 → 码位」的唯一映射。

**依据**

- `docs/conception/Instruction/2.截取指令.md`（局域存值现为 `&`）
- `docs/conception/Instruction/1.值指令.md`
- `docs/conception/Instruction/12.模式指令.md`

#### 回答

局域存值符号已从 `$` 改为 `&`。在 [截取指令](../docs/conception/Instruction/2.截取指令.md) 的说明里已经取消了 `&(1)` 用名称引用，并且说明了原因。

值指令中 `''` 虽然对应两个指令码位（3|4），但这只是一种文本源码表达，它们可以通过具体的值（大小范围）来区分。脚本中实际存储的是指令码序列，因此可以在前期源码编译为指令码时解决，前期编译是离线的，性能并不是一个问题。

`{}` 指令名同时表达三个指令码：整数、大整数和浮点数。整数和大整数通过大小来编译区分，浮点数通过值必须带小数点（`.`）来区分。

其它几个相同文本指令名对应多个指令码位的问题，也是相同的逻辑，它们都可以通过解析值和书写样式（字符顺序）来区分，这是一个细活，但确实可明确区分。

#### 评审回复

接受。`''`、`{}` 等一个文本名对应多个码位的情况，都能按值的大小和书写形式唯一确定码位，这只影响离线编译器。配合 P0-6 回复中的规范解码规则（例如 BigInt 不能编码 int64 范围内的值），反编译再编译能得到相同的字节码。

Spec 里会附一份正式文法（EBNF）和「文本 → 码位」的判定规则，供编译器和反编译器共用。

还有一处需要单独的规则：`12.模式指令.md` 中 `^'A'?` 写着「兼容两个指令（opcode:3|4）」。一条模式指令在字节码里只有一个码位，要同时匹配 3 和 4，需要规定匹配器对字节与符文字面量按值比较。

> **作者修订：**
> 「`^'A'?` 兼容两个码位」的设计已取消，现按编译后的实际指令值匹配（不另立规则）。
> - `^'A'` => opcode:3 A
> - `^'\u0041'` => opcode:4 A
>
> 另外添加了 `!Char` => 匹配任意字节和符文。这由类型匹配指令（opcode:122）负责。


### P2-5 值语义与引用别名

**问题**

TOP / TOPS / CLONE 是浅复制。SLICE 是在原切片上截取引用。SET / DEL / CLEAR 就地修改字典。评审时，除字典外没有就地修改指令，因此面向切片的 COPY / DCOPY 几乎没有可观测的意义。反过来，EXTEND 若用 append 在子切片上实现，会写穿父切片。

**建议**

定义「除字典外的值不可变，运算结果总是新分配」，或者让字典也不可变（SET 返回新字典）。

**依据**

- `docs/conception/Instruction/4.集合指令.md` SLICE、SET
- `docs/conception/Design.md` 特性指令中的 DICT
- `docs/conception/Instruction/14.工具指令.md` COPY

#### 回答

已经删除了 `DCOPY` 指令，另外 `COPY` 指令已调整了操作对象，这是对字典对象复制的需求（之前遗失了）。字典值本身只是引用浅复制，因为没有方法可以修改引用的值本身，所以这是安全的。

指令 `EXTEND` 已经明确要求返回一个新的副本，底层片段先复制。

是的，除字典外，其它所有指令的值实际上都不可变，即便 `SLICE` 是在原底层数组上引用。这由各指令在实现保证。切片在原有底层上引用会有更好的效率，我觉得是值得的。因为系统不提供修改底层值的指令，会影响底层值的指令都是要求返回新值。

#### 评审回复

接受：除字典外的值都不可变；SLICE 共享底层数组；EXTEND 先复制再扩展。

有一处例外需要处理。COPY 的说明是「键对应的值本身不能被修改，所以浅复制没有问题」。但字典的值可以是另一个字典，而字典可以被 `SET` 修改。浅复制之后，两个字典共享同一个内层字典，对它的修改会同时可见。

更严重的是循环引用：`SET` 可以把字典放进它自己（直接放入，或者先打包进一个切片再放入）。之后对它做 `PACK`、比较、打印这类递归操作，会无限递归。

建议用一条规则同时解决这两个问题：**字典的值（递归地，包括值里的切片成员）不能包含字典。** 在 `DICT`、`SET`、字典合并时检查，违反即失败。切片不可变，只能由已经存在的值构造，本身形不成循环；只有字典是可变的，所以只需约束字典。这样 COPY 的浅复制也就真正安全了（Q5）。
