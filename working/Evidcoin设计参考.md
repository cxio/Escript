# Evidcoin 部分设计参考

## 签名

对输出项的*拥有权*通常通过签名来证明。这也是系统内置验证的标准方式。

签名可以是简单的**单签名**模式，即输入项的来源输出是属于一个单公钥哈希，因此也仅由一个私钥对应。

签名还可以是复杂的**多重签名**，即输入项的来源输出是属于一个复合公钥哈希地址，该地址实际上由多个公钥构成，因此也就对应多个私钥。

- **单公钥哈希**：由一个私钥对应一个公钥，对公钥的哈希结果。
- **复合公钥哈希**：由多个公钥根据规则构造的序列，对该序列的哈希结果。因此对应多个私钥。

**注：**
- 单公钥哈希与复合公钥哈希在外观上没有区别（隐私安全），但它们的验证逻辑不同。


### 单签名

交易的输入项来源于单公钥哈希，签名仅需单一私钥。

这是大多数交易的实际情况，即便交易里有多笔输入，它们都来源于单公钥哈希地址。

> **注：**
> 包含多笔单公钥哈希输入的交易，需要这些输入项的全部签名。

单公钥哈希的算法：`SHA3-256( BLAKE2b-512(pubKey) )`。


### 多重签名

适用于复合公钥哈希地址，需要由多个私钥共同进行签名才行。此即为*多重签名*，也即所谓的**多签**（简称）。

多签支持 `M-Of-N` 的工作机制，以增强社会化的安全性和灵活性。

- N：总共需要的私钥数量（参与方的公钥总数）。
- M：实际需要签名授权的最少私钥数量（M ≤ N）。如：`2-of-3` 多签地址表示有3个私钥，任何2个私钥签名即可。

> **注：**
> 内置验证对单签名或多重签名的判断由解锁数据中的见证信息指明。


#### 多重签名的地址

准备 N 个公钥，及 M/N 的配比（如：`2/3`）。

构造流程：

0. 对N个公钥执行简单的哈希运算 `BaseH = BLAKE3( pubKey )`，得到N个公钥的*初级哈希*。
1. 对N个公钥的初级哈希按字典序排序&串连：`BaseHAll = Concat( Sort(BaseH1, BaseH2, ... , BaseHn) )`。
2. 在串联结果 `BaseHAll` 前置 `m/N` 配比，计算复合公钥哈希：`PKHmix = SHA3-256( BLAKE2b-512( <m/N> + BaseHAll ) )`。
3. 复合公钥哈希（`PKHmix`）编码为文本形式，即为多重签名的账户地址。

> **说明：**
> `m/N` 配比为 `1+1` 两个字节，因此最多支持 `255/255` 的组合规模。
> `m` 和 `N` 任一值不得为零，否则不合法。

每一位参与者的公钥有一层初级的哈希封装（`BLAKE3`），这会更安全。在外观上，多签地址与普通地址也没有区别（隐私安全）。

另外，这种安全性可能让参与者更自由，比如匿名参与会更容易。


#### 多重签名的验证

见证信息：

- **签名集**：`m/N` 中 `m` 个私钥对交易的签名。
- **公钥集**：上面 `m` 个签名对应的公钥序列。
- **补全集**：未参与签名的公钥的初级哈希（`N-m` 个）。

> **注：**
> 组合配比 `m/N` 可由公钥集大小和补全集大小计算而来。

验证过程：

0. 计算 `m/N` 配比。
1. 计算公钥集里各个公钥的初级哈希。
2. 结果集与补全集里的初级哈希混合排序、串联，前置 `m/N` 配比，计算复合公钥哈希。
3. 对比接收者的公钥哈希与上面计算的结果，相同时有效。
4. 验证签名集里的各个签名。


### 签名消息

通过对签名消息的不同约束，签名授权可以有多种模式。


#### 授权种类

由**1**个字节配置签名消息的约束目标：

```go
// 独项：
7] SIGIN_ALL    全部输入项，含解锁脚本，不含见证信息。
6] SIGIN_SELF   当前输入项（自身），含解锁脚本，不含见证信息。
// 主项：
5] SIGOUT_ALL   全部输出项：适用于币金、凭信、存证
4] SIGOUT_SELF  与当前输入项同序位的输出项
// 辅项：
// 需配合 SIGOUT_SELF 或 SIGOUT_ALL 使用。
3] SCRIPT       输出项的脚本。
2] CONTENT      输出项的内容：除脚本和接收者之外的全部条目。
1] RECEIVER     输出的接收者。
0] OUTPUT       输出项的全部（脚本+内容+接收者），友好。
```

**说明：**

- 「独项」逻辑自完整。可独立设置，也可与其它设置合并使用。不含见证（签名/公钥）。
- 「主项」不能独立设置，需与辅项配合。如：`SIGOUT_ALL|RECEIVER`，锁定全部输出项的接收者。
- 「辅项」需与主项配合使用。如：`SIGOUT_SELF|SCRIPT|CONTENT`，锁定当前输入项同序位输出项的脚本和内容。

> **提示：**
> 所有签名消息都默认包含交易头内的版本信息、时间戳和铸凭公钥哈希（如果有）。
> 未指定的部分不会包含，因此可以被第三方修改而不影响签名验证。
> OUTPUT 选项与 SCRIPT/CONTENT/RECEIVER 为互斥关系，不应同时使用。
> 解锁段如果提供了签名和公钥，其仅用于入栈，不计入解锁脚本内容（解锁脚本中以系统占位符 `<Sig>`、`<PubKey>` 等代替，见 Escript 的 `Design.md`「附：系统占位符」）。

**注意**：此授权种类功能仅用于普通交易，Coinbase 交易无此功能，是直接对整个交易进行签名。



## 交易的合法性

交易是否合法，主要由输入项的验证结果决定：解锁数据+锁定脚本的执行判定，以及签名的合法性。

但一笔交易还有其它一些规则需要满足。


### 前置检查

交易的输入项是前一笔交易的输出项，该输出项的接收者即为当前交易的花费者。

币金和凭信的花费逻辑不同，当前输入是哪一种信元，需要从来源脚本的「输出项配置字节」中读取。并据此进行相应的合规性检查。

**币金：**
- 每一笔币金输入项都必须存在于 `UTXO` 集内且未花费。
- 输入项的总金额必须大于输出项的总金额，且差额必须大于等于最低交易费。
- 首笔输入必须是币金花费，且币权是全部币金输入项里最大的（首领输入约束）。
- 每一笔输出项的币金数量必须大于零，零币金输出非法。
- Coinbase 交易无输入项，但输出项的金额和格式必须合规。

**凭信：**
- 每一笔凭信输入项必须已经存在于 `UTCO` 集内且未消费。
- 一笔交易里最多仅能包含**2**笔凭信输出，此为协议。
- 如果存在第二笔凭信输出，交易费应当大于前一阶段平均交易费的**2**倍。不过此项可由区块打包者自由裁量。
- Coinbase 交易中不能包含凭信输出。

**安全限制：**
- 输出项中各字段值的长度必须满足系统设计的限制要求（如标题长度、内容长度、脚本长度等）。
- 各输出项的版本号必须合法，但无需限定其必须为当前最新版本。不存在的版本号无效，交易非法。



## 交易输出项

接受币金支付或凭信转移的目标（目的地）。

一笔交易中可以有多个输出项。对于币金交易来说，可能包含一个收款者和一个找零地址。对于凭信转移交易，则逻辑上只有一个接收者。

每一笔*输出*包含了特定类型「信元」的相关字段信息（详见『信用结构』中相应的信元定义）。


### 配置/状态

输出项包含前置**2**字节的版本号和状态/配置记录：

- `[0]` 首字节设定版本号。
- `[1]` 状态/配置：高4位为状态位，低4位为类型值。

**状态/配置：**

```go
 7] 包含附件：标记该输出项是否包含附件。
 6] （未用）
 5] 内容摘要：内容长度超出规定，将使用其哈希（`BLAKE3`）参与计算输出项摘要。
 4] 脚本摘要：同上逻辑，但针对脚本。
[4] 类型说明：低4位值。
    0) 预留：暂无意义。
    1) 币金：输出为币金支付。可以作为输入源。
    2) 凭信：输出为凭信。可以作为输入源。
    3) 存证：输出为存证，不能作为输入源。常用于介管脚本定义。
```

> **摘要状态：**
> 如果目标数据大于**64**字节，即强制标记并实施。此为状态记录，非用户配置。
> 可用于历史脚本验证，比如 `GOTO` 跳转需要的目标脚本：用户仅需提供脚本内容和少量的其它数据即可。

这里的**内容**指输出项的内容部分，即除「脚本」和「账户/接收者」之外的其它全部条目。

如果输出项包含附件，在最高位标记，这是一种友好：外部应用无需先解析输出项数据即可确定附件的存在。
